# ADR-0036 沙箱镜像、集群与驱动的补充约定

| 项 | 内容 |
|---|---|
| 状态 | 已采纳（补充） |
| 日期 | 2026-11-08 |
| 决策人 | T11 执行会话 |
| 影响的架构设计章节 | 「端口」（新增 `SnapshotStorePort`）、「会话沙箱」、「沙箱 Pod 与镜像」、「沙箱出网」（只补充，不改既有条款） |

## 背景

T11 实现沙箱镜像、集群侧的模板与预热池、`SandboxDriver`，并在本机 kind 集群（gVisor、Calico、agent-sandbox v1.0.10）上验证 P5。架构设计规定了镜像约定的三个接口、模板的安全要求、三个规格、快照存对象存储与 `SingleStartSandbox`，落地时遇到以下没有写到或与实际情况有出入的细节：

- **镜像接口的完整约定。** AgentScope 2.0.4 的扩展除了 `POST /execute`、`/upload`、`/download`，还调用 `GET /list/{路径}`、`GET /exists/{路径}`；`/execute` 只发送 `command`，不带超时，每次 HTTP 尝试的超时默认 60 秒（`perAttemptTimeoutSeconds`），而且不重试；快照恢复时上传 `.agentscope-tmp/…` 之前不建目录（`KubernetesSandbox.hydrateViaFileApi`）。
- **连接方式依赖 sandbox-router。** 扩展的三种连接方式（`KubernetesSandboxClient.toConnectionConfig`）都经 sandbox-router 转发：端口转发是对沙箱命名空间中 `sandbox-router-svc` 的 Pod 的 8080 端口转发，直连与网关同样带 `X-Sandbox-ID`、`X-Sandbox-Pod-IP` 请求头访问 router。agent-sandbox v1.0.10 的发布清单（`sandbox-with-extensions.yaml`）只有控制器与 CRD，Go 版 router 的镜像是 `registry.k8s.io/agent-sandbox/sandbox-router-go:v1.0.10`，部署清单只在仓库的 `sandbox-router/deploy/` 中，且默认装在 `agent-sandbox-system`。
- **模板的网络策略默认放开公网。** `SandboxTemplate.networkPolicyManagement` 默认 `Managed`，不写 `networkPolicy` 时控制器生成的默认策略"只允许访问公网"（v1.0.10 `extensions/api/v1beta1/sandboxtemplate_types.go`），与"沙箱默认无出网"相反。
- **emptyDir 挂载点属于 root。** `fsGroup` 只改属组，非 root 用户不能修改挂载点本身的时间与权限；扩展恢复快照时执行 `tar -xf <归档> -C /workspace`，归档根目录 `.` 的时间与权限无法设置，`tar` 以退出码 2 结束（kind 实测：`Cannot utime`、`Cannot change mode`），恢复被判为失败。`--no-overwrite-dir`、`-m` 都不能避免对 `.` 的 chmod。
- **进程数上限。** 架构设计为三个规格规定了进程数（256、512、1024），Pod 规格里没有按 Pod 设置 PID 上限的字段（kubelet 的 `podPidsLimit` 是节点级配置）。
- **快照存储的入口。** engine-agentscope 不能依赖 persistence（「模块依赖规则」），`BlobStorePort` 的键由实现生成，满足不了架构规定的快照路径。
- **驱动错误的类型。** runtime 不能引用 AgentScope 的异常，需要平台类型区分"沙箱已不存在"与"暂时不可用"。

## 候选方案

**sandbox-router**

- A：按上游 `sandbox-router/deploy/` 装在 `agent-sandbox-system`。扩展的端口转发在沙箱命名空间中找 router（`LocalTunnelConnectionConfig` 的 `routerNamespace` 取沙箱命名空间），本机开发连不上。
- B（采纳）：由 `deploy/helm/meridian-sandbox` 把 router 部署在沙箱命名空间，服务名 `sandbox-router-svc`、端口 8080（扩展的固定约定）。关闭 Pod IP 缓存（扩展每次请求都带 `X-Sandbox-Pod-IP`），因而不需要访问 API、不挂载令牌；router 的出网只到本命名空间的沙箱 Pod 的 8888，入网只允许 runtime 所在的命名空间；代理超时 660 秒，大于命令超时。

**网络策略**

- A：`Managed` 并在模板里写 `networkPolicy`。出网规则交给控制器生成，T12b 加代理规则时还要按控制器的子集语法写。
- B（采纳）：模板设 `networkPolicyManagement: Unmanaged`，chart 自带两条 NetworkPolicy：沙箱 Pod 拒绝全部出网，入网只允许 router 访问 8888；T12b 在此基础上加一条只到出网代理的规则。

**工作区目录**

- A：以 root 运行初始化容器修改挂载点属主。违反"非 root"与命名空间的 Pod Security `restricted`。
- B：快照恢复改为平台自己展开归档。绕开 harness 的恢复分支，`SandboxContext` 中的外部沙箱仍走 harness 的逻辑。
- C（采纳）：emptyDir 挂在 `/var/lib/sandbox`，入口脚本以 uid 1000 创建 `/var/lib/sandbox/workspace`，镜像中 `/workspace` 是指向它的符号链接（根文件系统只读，智能体删不掉链接）。镜像的工作目录不能是 `/workspace`：容器启动时链接目标还不存在，运行时会以 root 创建它。

**进程数**

- A：kubelet 的 `podPidsLimit`。节点级，三个规格无法不同。
- B（采纳）：入口脚本 `ulimit -u $SANDBOX_MAX_PROCESSES`，执行服务启动的命令都继承它。gVisor 中每个 Pod 有自己的内核，RLIMIT_NPROC 只统计本沙箱的进程（kind 实测：一个沙箱占满 246 个进程时，另一个沙箱仍能启动 200 个；超过上限时 `fork` 返回 `EAGAIN`）。依赖 RuntimeClass 必须是 gVisor；换成 runc 时同一节点上 uid 1000 的进程会合并计数。

**快照存储**

- A：扩展 `BlobStorePort`，允许调用方指定键。改变既有端口的语义（键由实现按会话生成、读取只认本会话前缀）。
- B（采纳）：engine-spi 新增 `SnapshotStorePort`（同步的 `put`、`open`、`exists`，只接受 `rt/snapshots/` 之下的键），runtime 的 `sandbox.app.ObjectStoreSnapshotStore` 实现；驱动按 `PlatformContext` 生成键 `rt/snapshots/{tenant_id}/{project_id}/{session_id}/{snapshot_id}.tar`（`snapshot_id` 为 ULID），并作为 AgentScope `RemoteSandboxSnapshot` 的 ID，序列化后的沙箱状态可以直接定位快照。方法是同步的，原因与 `WorkspaceStorePort` 相同：AgentScope 的 `RemoteSnapshotClient` 是同步接口。

## 决策

1. **执行服务**（`sandbox-runtime/`，Python FastAPI）实现扩展调用的五个接口，字段逐一对齐（对照表见 `sandbox-runtime/README.md`），并兼容 agent-sandbox 参考运行时 `examples/python-runtime-sandbox`：`/execute` 用 `/bin/bash -c`，服务端超时上限默认 600 秒（`SANDBOX_EXEC_TIMEOUT_SECONDS`，请求的 `timeout_seconds` 只能缩短），超时退出码 124；stdout、stderr 各保留 1 MiB；每条命令一个新进程组，命令结束或超时后整组 SIGKILL（后台进程不存活，要常驻须 `setsid`），组长被回收前发信号，组 ID 不会被并发命令复用；`/upload` 自动建上级目录；越出工作区的路径（含符号链接）返回 403。1 号进程为 `tini`，回收逃出进程组的孤儿进程。
2. **镜像**：Debian trixie slim、uid 1000、uv 管理的 Python 3.13 与文档处理库在同一虚拟环境、Node.js 24、文泉驿微米黑字体；`HOME` 与各类缓存在 `/tmp`；`/workspace` 为符号链接（候选方案 C）。
3. **集群侧**：`scripts/dev/install-agent-sandbox.sh` 按 v1.0.10 发布清单安装控制器（校验清单 SHA-256 与镜像标签，server-side apply）；chart `meridian-sandbox` 安装在命名空间 `meridian-sandbox`（Pod Security `restricted`），每个规格一套同名的 `SandboxTemplate` 与 `SandboxWarmPool`（`sandbox-small` 等），模板 `Unmanaged`，`automountServiceAccountToken: false`、`enableServiceLinks: false`；`disk` 为容器的 `ephemeral-storage` 上限与工作区 emptyDir 的 `sizeLimit`，`/tmp` 另限 1 GiB；chart 另含 router 与 runtime 的 Role（认领与删除 `SandboxClaim`、读 `Sandbox`、端口转发）。
4. **驱动**（`engine.agentscope.sandbox.KubernetesSandboxDriver`）：`create` 在 claim 上打标签 `meridian.refinex.cn/session-id`，执行一次 `start()`；`resume` 先确认 claim 与 `Sandbox` 都存在（扩展的 `getSandbox` 在 claim 不存在时会等满 30 秒），否则以 `NotFoundException` 失败；`restore` 把快照放进新沙箱的状态，由 harness 的"从快照恢复"分支展开；`delete` 关闭连接并删除 claim。本节点连接过的沙箱按 claim 名缓存为 `SingleStartSandbox`，`attach(state)` 供 T12a 放进 `SandboxContext.externalSandbox`。基础设施失败转为 `SandboxUnavailableException`（engine-spi，可重试，错误码 `sandbox.unavailable`）。扩展合并单次选项时非空字段一律覆盖默认值，所以单次选项要完整设置命名空间、工作区、端口；每次 HTTP 尝试的超时取命令超时加 60 秒。
5. **连接方式**：本机开发用端口转发（每个沙箱一条到 router 的转发，删除时释放）；生产环境 runtime 在集群内，推荐直连 router 服务（`SandboxDriverSettings.Direct`，`http://sandbox-router-svc.meridian-sandbox.svc.cluster.local:8080`），runtime 在集群外时用网关（Gateway API）。runtime 的配置项与装配在 T12a。
6. **kind 测试**：类名 `*KindIT`、JUnit 标签 `kind`，默认排除，`-Pkind` 时只运行它们（与 `live` 相同的写法）。

## 影响

- 架构设计：「端口」表增加 `SnapshotStorePort`；「会话沙箱」补充驱动的行为与连接方式；「沙箱 Pod 与镜像」补充 sandbox-router、`Unmanaged` 网络策略、工作区符号链接与进程数的实现；版本升至 v1.12。
- 新增：`sandbox-runtime/`、`deploy/helm/meridian-sandbox/`、`scripts/dev/install-agent-sandbox.sh`、`scripts/dev/deploy-sandbox.sh`；engine-spi 的 `SnapshotStorePort`、`SandboxErrorCode`、`SandboxUnavailableException`；persistence 的 `ObjectStore.exists`；`scripts/dev/verify.sh` 增加 sandbox-runtime 的 Ruff、mypy、pytest。
- 风险：router 以 `allow-all` 运行，能访问 router 的调用方可以操作任意沙箱，所以 router 的入网只放行 runtime 的命名空间，必要时改用 `scoped-token`；进程数上限依赖 gVisor；扩展把快照归档整个读进内存（`byte[]`），100 MB 的工作区在 runtime 侧占用同等内存，容量评估见 P5 报告。
