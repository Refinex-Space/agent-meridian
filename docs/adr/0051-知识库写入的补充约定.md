## 背景

T18 建立 knowledge 服务的写入一侧。架构设计给出了流程（对象存储 → `ingestion_jobs` → 解析 → 切分 → Embedding → `kb.chunks`）、四张表的关键列、`SKIP LOCKED` 与"退避重试 3 次"、目标 512 token 与重叠 64 token，以下几处没有写到：

- **向量维度。** 架构写 `embedding vector(n)`，任务要求维度"来自所选 Embedding 模型，配置化"；pgvector 的列类型在建表时定下。
- **知识库用哪个 Embedding 模型。** 模型属于租户的目录（ADR-0045），knowledge 经 runtime 的内部接口调用，需要模型 ID。
- **解析器的选择。** "常规 PDF 用 PDFBox，扫描件、复杂表格交给 doc-parser"，但上传时不知道一份 PDF 属于哪一类；PDFBox 也给不出标题与表格结构。
- **失败与崩溃。** 解析与 Embedding 可能持续数分钟，进程可能在中途退出；重新处理时旧切片在新切片就绪前是否可用。
- **存储量怎么计量。** 架构写"每日统计，计量单位 GB 天"，没有写统计什么、重算时怎样不重复上报。
- **授权。** API Key 的作用域已有 `knowledge:read`、`knowledge:write`，角色矩阵没有知识库的操作类别；控制台用户在公开 API 上的作用域由角色换算（ADR-0044）。
- **control-plane 校验知识库存在。** T15b 留下开发实现（`TODO(T18)`），control-plane 没有调用其他服务的出站凭据——它自己就是服务 JWT 的签发方。
- **doc-parser 的接口与认证。** 架构只写了"复杂文档解析为 Markdown"。

## 候选方案

**向量维度**

- A：迁移里写死 `vector(1024)`。换模型要改已合入的迁移。
- B（采纳）：迁移用 Flyway 占位符 `${embedding_dimensions}`，取配置 `meridian.knowledge.embedding.dimensions`（默认 1024，与 `qwen3.7-text-embedding` 相同）；启动时核对 `kb.chunks.embedding` 的实际维度与配置一致，不一致则启动失败。调用 Embedding 时带 `dimensions`，返回的向量长度不符时本次写入以不可重试的错误结束。

**知识库的 Embedding 模型**

- A：全局配置一个模型 ID。模型属于租户，全局 ID 只对一个租户有效。
- B（采纳）：创建知识库时指定 `embedding_model`（本租户目录中的 Embedding 模型 ID），之后不能修改；同一知识库的向量出自同一模型。模型不存在或种类不符由 runtime 返回 404、400，写入以不可重试的错误结束。

**解析器的选择**

- A：PDF 一律交给 doc-parser。常规 PDF 也要付出版面模型的开销，doc-parser 不可用时任何 PDF 都写不进去。
- B（采纳）：按 Tika 检测的媒体类型路由。Markdown 与纯文本用内置的结构解析；Office、HTML、RTF、ODF 用 Tika（POI）输出 XHTML，再转成中间表示；图片交给 doc-parser。PDF 先用 PDFBox 检查：文字层稀疏（平均每页可见字符少于阈值，视为扫描件）或页面上有框线围成的网格（视为表格），交给 doc-parser；否则用 PDFBox 抽取文字，按字号推断标题层级。doc-parser 没有配置而文档需要它时，写入以不可重试的错误 `document.parser_unavailable` 结束；配置了但暂时不可用时按退避重试。

所有解析器的结果都转成同一个中间表示（标题、段落、列表项、表格，带页码），切分器只依赖它。

**作业的失败与崩溃**

- A：失败即标记失败，由调用方重新处理。不满足"退避重试 3 次"。
- B（采纳）：每次上传、重新处理各建一个作业。认领用 `FOR UPDATE SKIP LOCKED`，同时写租约（默认 5 分钟），执行期间每分钟续一次；租约过期的作业由下一次认领收回，计为一次失败的尝试。错误分为可重试（doc-parser、runtime、对象存储暂时不可用，429、5xx）与不可重试（格式损坏、类型不支持、模型不存在、维度不符）。可重试的错误最多重试 3 次（共 4 次尝试），间隔 30 秒起每次翻倍；之后作业与文档标为 `failed`，带错误码与说明。
- 写入结果在一个事务中完成：锁住文档行，确认作业仍是本次尝试（`attempts` 相同且为 `running`），删除该文档的旧切片、插入新切片、更新文档与作业。重新处理期间旧切片仍可被检索，新切片就绪时一次替换；重新处理失败时保留旧切片。文档在执行期间被删除时，最终事务找不到文档行，结果被丢弃。

**切分**

- 按标题层级把文档分成节（同一标题路径下的连续块），节内按段落装箱到目标 512 token；超过目标的段落按句末标点拆分，仍超过时按长度硬切。相邻切片在同一节内重叠约 64 token（从上一片末尾按句子回取）。表格整体成为一个切片，不与正文合并；超过 `max-table-tokens`（默认 2048）时按行拆成多片，每片重复表头。
- token 用 `common.text.TextTokens.approximate` 估算：贴近 Qwen 系 BPE 分词（汉字约 0.7 个、英文单词约 1.3 个、数字逐位、标点各 1 个）；`TextTokens.estimate` 为预扣偏多估算，不用于切分。
- 每个切片记录来源定位 `source_locator`：文档 ID、文件名、起止页码（Office 与 Markdown 没有页码，为空）、标题路径。Embedding 的输入与全文索引都是"标题路径 + 正文"，`content` 只存正文。

**存储计量**

- A：每次写入、删除时上报增量。删除与重新处理会产生负数，账本只追加、数量不能为负。
- B（采纳）：每天（UTC）为每个有内容的知识库上报一条用量，种类 `knowledge_storage_gb_days`，数量是当天结束时的字节数除以 10^9（一天的 GB 天，账本保留 6 位小数），属性带 `knowledge_base_id`、`file_bytes`、`index_bytes`、`day`。字节数是原文件大小加切片正文与向量（每维 4 字节）的大小，后者在写入切片时算好存进文档行。`kb.storage_reports(knowledge_base_id, day)` 与 outbox 在同一事务写入，重复执行同一天不会重复上报。统计反映执行时的大小，不是当天的平均值。

**授权**

- 新增项目级操作类别 `KNOWLEDGE_READ`、`KNOWLEDGE_WRITE`：所有者与项目开发者读写，租户管理员与项目观察者只读，审批人没有。`PublicApiScopes` 把 `knowledge:read`、`knowledge:write` 映射到它们，控制台用户经 `Meridian-Project` 调用知识库接口时据此授权。

**control-plane 校验知识库**

- A：control-plane 直接读 `kb` schema。违反"服务只读写自己的 schema"。
- B（采纳）：knowledge 提供 `GET /internal/v1/knowledge-bases/{knowledge_base_id}`（调用方 `control-plane`、`runtime`），返回知识库的租户、项目与 Embedding 模型，不存在 404。control-plane 发布智能体版本时调用它，并要求租户与项目一致；它的出站服务 JWT 由本进程的签发用例直接签发（`sub` 为 `control-plane`），不经令牌端点。没有配置 `meridian.control-plane.knowledge.url` 时，引用了知识库的发布返回 503 `service.unavailable`（knowledge 不可用时同样），不把"查不到"当成"不存在"，开发实现 `ConfiguredKnowledgeCatalog` 删除。

**doc-parser**

- 接口：`POST /v1/parse`（`multipart/form-data`，字段 `file`、可选 `filename`），返回 JSON：`markdown`、`blocks`（类型、文本或表格的 Markdown、标题层级、页码、标题路径）、`page_count`、`parser`。PDF 的标题层级 Docling 只给出一层，doc-parser 按中文编号（"第一章""第一节""一、""（一）""1." 等）推断层级；汉字之间因换行产生的空格被去掉。
- 默认后端 Docling：版面模型、TableFormer（快速模式）与 RapidOCR 的中文模型在镜像构建时下载并固化，运行时 `HF_HUB_OFFLINE=1`；公式、图片分类、VLM 等模型不下载。MinerU 是可选后端（`DOC_PARSER_BACKEND=mineru`，构建参数 `WITH_MINERU=true` 才安装，许可证需使用方核对），默认镜像不含它。
- 认证：doc-parser 不校验服务 JWT，只在集群内网暴露，由 NetworkPolicy 限定只有 knowledge 能访问（T28 落实）。它不持有数据、不调用其他服务，解析的是已经授权上传的文件。

## 决策

采用以上各项的 B 方案。

## 影响

- 架构设计：知识库架构的写入流程补充解析器路由、作业的租约与重试、切分细节；核心表 `kb` 的列与 `storage_reports`；ID 前缀 `chk`（切片）、`ijb`（写入作业）；授权一节补知识库的操作类别；资源表写明知识库的端点；计量项写明 `knowledge_storage_gb_days`；内部接口补 `GET /internal/v1/knowledge-bases/{id}`。
- 代码：`meridian-knowledge`（迁移 `kb/V0001`）、`meridian-model-client`、`doc-parser/`；`meridian-common` 的 `IdPrefix`、`TextTokens.approximate`；`meridian-security` 的 `Permission`、`RoleMatrix`、`PublicApiScopes`；control-plane 的 `UsageKind`、`UsageMessages`、迁移 `V0006`（`usage_records.kind` 的检查约束）、`KnowledgeCatalogClient` 的实现与 `ServiceTokenIssuer` 的进程内签发；`meridian-test-support` 的用量样本。
- 风险：PDF 的路由靠启发式，框线不完整的表格会被 PDFBox 当作正文切分；扫描件的阈值对极短的文档可能误判。路由结果记在文档的 `parser` 字段，可以按文档排查。knowledge 调用内部模型接口时只带租户与项目，知识库没有进入账本的维度（登记事项）。
