# ADR-0032 模型调用、计量与压缩守护的补充约定

| 项 | 内容 |
|---|---|
| 状态 | 已采纳（补充） |
| 日期 | 2026-11-08 |
| 决策人 | T09a 执行会话 |
| 影响的架构设计章节 | 「端口」、「引擎装配」中的 `compaction` 行、「平台中间件」、「事件映射」中的 `CUSTOM` 行、「上下文管理」、「模型调用」、「计量与预算」（只补充，不改既有条款） |

## 背景

T09a 落地 `RoutedModel`、`ModelGateway` 的 runtime 实现与压缩守护。架构设计规定了四个步骤、错误处理的原则与两层守护的职责，按 AgentScope 2.0.4 源码落实时有几处没有写到、又会被 T09b、T15a、T16、T19 依赖的细节，其中三处是 2.0.4 的行为带来的缺口：

- **拿不到 `Retry-After`。** 2.0.4 的 `JdkHttpTransport` 在流式路径上只保留状态码与正文，`OpenAIClient` 把它翻译为不带响应头的 `OpenAIException`。架构设计要求 429 时重试，测试要求覆盖 `Retry-After`。
- **失败的摘要已经写进状态。** `CompactionMiddleware.onReasoning` 在调用下游之前就执行 `applyToContext`，把智能体状态的上下文换成"摘要加尾部"；内层守护看到失败文本时，历史已被替换，随后的错误会让 AgentScope 把它保存下来（P13 的对照实验复现了这一点）。
- **压缩事件没有出口。** 中间件只能经 `Flux<AgentEvent>` 向事件流输出，2.0.4 的 31 个事件类型里能承载平台事件的只有 `CUSTOM`，而「事件映射」表把 `CUSTOM` 定为只记日志。

另有一处与任务描述不同：T09a 的任务写"装配时 `maxRetries(0)`"，2.0.4 中 0 非法，ADR-0023 已改为 `maxRetries(1)`，本 ADR 沿用。

## 候选方案

**`Retry-After` 的来源**

- A：在 `OpenAIClient` 外层按状态码固定退避，不读 `Retry-After`。供应商给出的等待时间被忽略，退避过短时连续撞限流。
- B：给 `JdkHttpTransport` 传一个装饰过的 `java.net.http.HttpClient`，在 `sendAsync` 里记下响应头，用线程局部变量关联到本次调用。依赖 2.0.4 内部的订阅时序，脆弱。
- C（采纳）：平台自己的 `HttpTransport` 实现 `ProviderHttpTransport`（JDK `HttpClient`，SSE 解析、首包与空闲超时、取消关闭连接与 2.0.4 一致），收到响应时把状态码与 `Retry-After` 记到 Reactor Context 中本次尝试的观察记录上。

**失败摘要的拦截**

- A：内层只抛异常。状态已被替换，历史丢失，不满足"不替换历史"。
- B（采纳）：外层在每次推理前把上下文副本放进 Reactor Context（`CompactionWatch`），内层发现失败时先恢复上下文再抛 `CompactionFailedException`。随后 AgentScope 保存的是恢复后的上下文。
- C：失败时不抛异常、恢复后不压缩继续推理。会话已经超过阈值，继续推理大概率超出窗口，且掩盖了预算等真实原因。

**压缩事件的出口**

- A：经 `EventSinkPort` 直接写库。与 Worker 写入的事件并行，顺序不确定，引擎层测试也看不到。
- B（采纳）：内层在下游事件之前发出名为 `meridian.context_compacted` 的 `CustomEvent`，事件映射按名字翻译为 `agent.context_compacted`，其余 `CUSTOM` 仍只记日志。

## 决策

**1. `ModelGateway` 的补充。** 增加 `describe(modelId)`（模型目录的上下文窗口与默认最大输出，不解析凭据，装配时设置 `setContextWindowSize`）与 `precheck(route, tokens)`（只检查、不占用，压缩前由外层守护调用）；`ModelRoute` 增加 `maxOutputTokens`；`settle` 的入参改为 `ModelCallRecord`（请求 ID、实际路由、智能体版本、用途 `reasoning`/`compaction`、用量、来源 `provider`/`estimated`、首 token 时间、是否降级）。没有生产实现在先，不改变既有语义。`ModelFactory.create` 增加智能体版本 ID，写进用量记录。

**2. 重试与降级。** 首包之前的连接失败、超时、5xx、429 重试 2 次：指数退避从 500 毫秒起，429 取 `Retry-After` 与退避的较大者；要求等待超过 10 秒的不原地重试，交给降级或重新排队。每次重试前重新等待限流，预扣只做一次；降级到备用模型时主模型的预扣被释放、备用模型重新预扣。首包之后的错误不重试、不切换，连接中断与 5xx 一类仍翻译为可重试的 `ProviderUnavailableException`（本轮置回队列），其余 4xx 为终止的 `ProviderRejectedException`。底层客户端每次调用都只尝试一次（`ExecutionConfig.maxAttempts(1)`），压缩器以空选项调用时也一样。

**3. 结算。** 用 `Flux.usingWhen` 包住一次调用（含重试）：完成、出错、取消都结算，结算在终止信号传给下游之前完成。收到过响应：有供应商用量按用量结算，没有时按估算的输入与已收到增量的估算输出结算并标为 `estimated`；没有收到任何响应：只释放预扣，不写用量记录。结算先写 outbox，再修正 Redis 计数、退回 TPM 桶多扣的部分；Redis 失败时计数偏多，由 T16 的对账以账本为准修正。结算失败只记日志，不影响本次调用的结果。

**4. token 估算。** ASCII 字符每 3 个算 1 个 token，其余字符每个 1 个，每条消息加 8 个结构开销，媒体与数据块按 1500；对英文与中文都偏多，预扣宁可多扣、事后退回。上下文构成摘要用同一套估算。

**5. 限流。** 令牌桶容量等于每分钟上限，按每毫秒 上限/60000 补充，RPM 与 TPM 两个桶在一个 Redis 哈希里用 Lua 原子检查与扣减；单次估算超过 TPM 时按桶容量计。时间取注入的 `Clock`（ADR-0027）。需要等待时按桶给出的时间等，累计等待会超过 30 秒时立即抛 `RateLimitTimeoutException`，不空等。限流参数取模型自己的，没有时取供应商账号的。

**6. 预算。** T09a 的预算以 token（输入加输出）计；四级计数都记（没有限额的级别也记，供对账），键 `budget:{租户}:used:{级别}:{范围 ID}` 带租户哈希标签，预扣记录保留 1 小时。限额经 runtime 内部端口 `BudgetLimitPort` 读取，开发实现读 `dev-config/budgets`，没有配置的级别不限；T16 改为 control-plane 同步到 Redis 的限额，是否换算为金额由 T16 决定。

**7. 用量记录。** outbox 主题 `usage`，载荷字段：`kind`（`model_tokens`）、`request_id`、`occurred_at`、租户、项目、API Key、智能体版本、会话、线程、轮次、`model_id`、`provider_account_id`、`upstream_model`、`purpose`、`fallback`、`usage_source`、`input_tokens`、`output_tokens`、`cache_read_tokens`、`cache_write_tokens`、`reasoning_tokens`。价格表版本由 control-plane 消费时确定。

**8. 供应商客户端。** 底层客户端按"供应商账号加模型（加端点）"缓存，构造时不放凭据，凭据与端点放在每次调用的选项中。T09a 实现 OpenAI 兼容类型（2.0.4 的 `agentscope-extensions-model-openai`）；Anthropic、Gemini 的模型类在 2.0.4 的扩展模块中存在，但分别引入 `anthropic-java`、`google-genai` SDK，没有加入，扩展点是 `ProviderClientFactory`。开发期的供应商目录读 `dev-config/providers`，凭据只写环境变量名，开发实现 `EnvironmentSecretResolver` 只允许读取以 `_API_KEY` 结尾的变量。

**9. 压缩配置与守护。** `CompactionConfig` 增加 `triggerMessages(0)`（关掉 2.0.4 默认的 50 条消息阈值，只按"窗口减 reserved"触发）与平台的摘要提示词。外层 order 20：按与 `CompactionMiddleware` 相同的阈值算法（未裁剪的会话计数）判断本次会压缩时，预检租约、预算与限流；每次推理都把 `CompactionWatch` 放进 Reactor Context。内层 order 0：把观察记录从推理调用的上下文中删除（`RoutedModel` 据此区分压缩调用）；摘要以 `(Summarization failed` 开头或为 `(Summary unavailable)` 时恢复上下文并抛 `CompactionFailedException`，原因取 `RoutedModel` 记在观察记录上的平台异常，事件映射沿原因链判定预算不足、可重试或终止。

**10. 事件映射中的 `CUSTOM`。** 新的处置类别 `PLATFORM_CUSTOM`：平台中间件以约定名字发出的 `CustomEvent` 按名字映射，目前只有 `meridian.context_compacted` → `agent.context_compacted`，其余只记日志。

**11. 上下文构成。** 平台中间件 `ContextCompositionMiddleware`（`onModelCall`，order 10）统计交给模型的消息：系统消息中 `<available_skills>` 块算技能清单（条数为技能数），其余算系统提示词；带 steer 或恢复说明标记的消息算注入内容（前置检索由 T19 加入标记）；工具消息算工具结果；其余算历史（含压缩摘要）。结果挂在 2.0.4 `ModelCallStartEvent` 的元数据上，事件映射放进 `span.model_request_start.context`。公开 API 增加 `ContextComposition`、`ContextPart`，属于兼容的新增字段。缓存命中 token 只在响应结束后可知，放在 `span.model_request_end.usage.cached_tokens` 与用量记录中。

## 影响

- 架构设计升至 v1.8：「引擎装配」`compaction` 行、「平台中间件」两行、「事件映射」`CUSTOM` 行、「上下文管理」「模型调用」「计量与预算」相应补充。
- 代码：engine-spi 的 `ModelGateway`、`SpanEvent.ModelRequestStart`、`ContextComposition` 与三个异常；engine-agentscope 的 `model` 包与两个中间件；runtime 的 `modelrouting` 上下文、`config` 中的凭据解析与模型工厂自动配置；OpenAPI 的 `SpanModelRequestStartData`。没有数据库迁移。
- 依赖：BOM 增加 `agentscope-extensions-model-openai` 2.0.4（enforcer 放行）与 `mockwebserver3` 5.3.2（只用于测试）。
- 风险：开发期的模型目录不区分项目，任何项目都能使用目录中的模型（T15a 改为按项目授权）；预算以 token 计，与 T16 的金额预算之间需要换算；外层的阈值判断可能在裁剪后不再压缩时多做一次预检，没有副作用。验证见 `docs/poc/P13-中间件顺序.md` 与 T09a 的验收记录。
