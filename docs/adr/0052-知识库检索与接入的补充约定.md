## 背景

T19 实现知识库的检索一侧与四种对外形态（`knowledge_search`、前置检索、REST、MCP Server）。架构设计给出了检索流程（可选改写 → 向量与全文各前 50 → RRF → rerank 前 k → 带来源定位返回）、过滤条件下推到 SQL、调用方标签来自会话的 `end_user_attributes.acl_tags`，以下几处没有写到：

- **rerank 与查询改写用哪个模型。** 模型属于租户的目录（ADR-0045），架构只写了"小模型""调用 runtime 的 `/internal/v1/rerank`"；runtime 也没有给 knowledge 用的对话接口。
- **不带标签的切片对谁可见。** 架构只写了 `acl_tags && :caller_tags`；公开 API 的 `EndUserAttributes` 写的是"只返回带有其中任一标签或不限标签的切片"。
- **共用的 HNSW 索引。** 所有租户的切片在一个索引里，按租户、知识库、标签过滤之后剩下的可能远少于 HNSW 默认扫描的近邻数。
- **全文召回的查询。** `plainto_tsquery` 把词项"且"连接，自然语言的问题几乎召回不到。
- **REST 与 MCP 的调用方标签。** 这两个入口没有会话。
- **多个知识库、多个 Embedding 模型。** 一次检索可以跨知识库，知识库的 Embedding 模型可能不同，不同模型的向量距离不可比。
- **检索的计量。** 登记事项 D70：检索次数没有计量种类。
- **MCP 客户端的重连。** 登记事项 D53 A-F8：MCP 连接在装配时建立、随实例缓存，服务重启后的语义未处理。

## 候选方案

**rerank 模型**

- A：knowledge 的全局配置。模型 ID 属于租户，全局配置只对一个租户有效。
- B：智能体配置。REST 与 MCP 没有智能体，这两个入口就不能重排。
- C（采纳）：知识库的可选属性 `rerank_model`（kb `V0002`），创建时指定，不设置时只按 RRF 排名返回。一次检索跨多个知识库时，取 ID 最小的、设置了模型的那个知识库的模型（只用一个模型，得分才可比；按 ID 选与请求中知识库的顺序无关）。

**查询改写**

- A：runtime 在调 knowledge 之前改写。改写属于检索流程的第 1 步，REST 与 MCP 以后要用时还得再做一次。
- B（采纳）：智能体配置的 `knowledge.query_rewrite_model`（可选，发布时校验是本租户的对话模型并记为引用），runtime 经内部检索接口传给 knowledge；knowledge 经 runtime 新增的内部接口 `POST /internal/v1/chat/completions`（只接受 knowledge，非流式、只有文本，与公开的对话补全共用 `RoutedModel` 的限流、预算与计量）改写，取输出的第一个非空行。改写失败只记 WARN、用原查询，不让检索失败。

**不带标签的切片**

- A：只有带交集的切片可见。上传时不写标签的文档谁都检索不到，与公开 API 的说明矛盾。
- B（采纳）：`acl_tags = '{}' OR acl_tags && :caller_tags`，与 `EndUserAttributes` 的说明一致；两个条件都能用 `acl_tags` 的 GIN 索引（`array_ops` 支持 `=` 与 `&&`）。调用方没有标签时只能看到不限标签的切片。

**共用的 HNSW 索引**

- A：每个租户或知识库一个部分索引。租户数不定，迁移管不了。
- B（采纳）：knowledge 的数据源在建连接时设置 `hnsw.iterative_scan = strict_order`、`hnsw.ef_search = 100`（pgvector 0.8，Hikari 的 `connection-init-sql`）：过滤后不够 50 条时继续扫描，且保持距离顺序。向量召回的排序只按距离（加上次序键规划器就用不上 HNSW 的有序扫描）。

**全文召回**

- B（采纳）：查询经 `to_tsvector('public.chinese', …)` 分词，词项逐个加引号、转义后以 `|` 连接直接转成 `tsquery`，按 `ts_rank_cd` 排序；`tsquery` 写成标量子查询（InitPlan 的参数），`tsv @@` 才能作为 GIN 的索引条件。

**REST 与 MCP 的调用方标签**

- REST（采纳）：请求体的 `acl_tags`，含义与会话的 `end_user_attributes.acl_tags` 相同；平台信任 API Key 所属项目声明的标签（架构设计「对外形态」）。读权限即可（`knowledge:read`），`POST` 照约定支持 `Idempotency-Key`。
- MCP：A 放进工具入参。调用工具的是接入方的大模型，它可以随意填写。B（采纳）：请求头 `Meridian-Acl-Tags`（逗号分隔），由接入方配置的 MCP 客户端声明；认证与公开 API 相同（API Key 或控制台用户加 `Meridian-Project`，按主体限流，要求 `knowledge:read`），工具按当前请求的主体与标签检索，不随 MCP 会话固定。工具不传 `knowledge_base_ids` 时检索本项目的全部知识库（至多 32 个）。

**多个 Embedding 模型**

- 采纳：每个 Embedding 模型一路向量召回（查询各算一次向量），加一路全文召回，各路一起进 RRF；不同模型的距离不在同一路里比较。

**检索计量**

- 采纳：用量种类 `knowledge_search_calls`（cp `V0007`），每次检索一条，带入口（`rest`、`mcp`、`agent`）、知识库与会话、轮次、API Key，只进账本、不占预算；查询改写、Embedding、rerank 的 token 照旧由 runtime 计量。

**MCP 客户端的重连**

- A：维持现状，等实例淘汰（空闲 30 分钟或新版本）。实测（T19，`McpToolsIT` 在原端口重启服务）：MCP Java SDK 0.17.2 在服务端返回 404 之后只在后台重新初始化，后台没有调用方的 Reactor Context，凭据到不了请求头，初始化被拒；之后的调用都加入这次失败的初始化，客户端在实例淘汰前一直不可用。
- B（采纳）：平台的 `tools.mcp.McpSession` 持有一个服务的当前客户端；调用因会话不存在（`McpTransportSessionNotFoundException`）、会话已终止、客户端初始化失败而失败时（这三种情况下服务端都没有执行这次调用），用本次调用的凭据新建并初始化客户端、换下旧的，再重试一次。并发调用只重建一次；工具清单仍是装配时发现的。

## 决策

采纳上面各项的 B（或标明的方案）。前置检索中间件 `KnowledgePrefetchMiddleware` 的 `order()` 为 150（只用 `onAgent`，在平台上下文与追踪之内），只挂在开启了前置检索的主智能体上：用本轮最后一条用户消息检索，把带来源标签的切片作为一条用户消息插在它之前（元数据 `meridian_knowledge_prefetch`，上下文构成计为平台注入内容），检索失败或没有命中时不注入。检索参数（向量与全文各 50、RRF k = 60、rerank 候选 20、默认 top_k 8）是 `meridian.knowledge.search` 的默认值，与检索评测（`docs/engineering/retrieval-evaluation.md`）一致。

## 影响

- 架构设计：「检索流程」「对外形态」补上模型来源、标签语义、HNSW 迭代扫描、全文查询、REST 与 MCP 的标签、计量；「平台中间件」补上前置检索的顺序与注入方式；「数据架构」的 `knowledge_bases` 加 `rerank_model`；「API 设计」的资源表补上 `/search`；「计量与预算」加 `knowledge_search_calls`。版本 v1.26。
- 规范：公开 `POST /v1/knowledge-bases/{id}/search`，`KnowledgeBase.rerank_model`、`CreateKnowledgeBaseRequest.rerank_model`，`UsageKind` 加 `knowledge_search_calls`；内部 `POST /internal/v1/knowledge-bases:search`（knowledge 提供，只接受 runtime）与 `POST /internal/v1/chat/completions`（runtime 提供，只接受 knowledge）；智能体规格的 `knowledge.query_rewrite_model`。
- 迁移：kb `V0002`、cp `V0007`。部署：runtime 配 `meridian.runtime.knowledge.url`，control-plane 的服务客户端 `runtime` 可以换取 `knowledge` 的令牌。
- 风险：MCP SDK 0.17.2 的服务端会话在进程内、没有过期（D82）；改写只看单条消息，追问式的问题（"那上海呢"）改写不好；检索评测集小、指标接近上限，守的是回归而不是区分度。
