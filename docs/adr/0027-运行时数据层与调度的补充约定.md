# ADR-0027 运行时数据层与调度的补充约定

| 决策人 | T05 执行会话 |
| 影响的架构设计章节 | 「核心表」、「一轮执行的生命周期」中的「认领」「租户并发计数行」「租约」「租约回收」「同节点重新认领」、「状态机」（只补充，不改既有条款） |

## 背景

T05 建立 runtime 的 `rt` 表结构、轮次调度与租约，以及 `LeaseRegistry`、`AgentStateRepository`、`EventSinkPort`（事件写入部分）的数据库实现。落实架构设计的调度与 fencing 规则时，有几处细节没有写到，而它们决定并发正确性、可测试性，以及 T06（Worker）、T07（API 与 SSE）、T14a（租户配额）如何接上。这些决定影响多个任务且一旦有数据就难以回退，所以记录在这里。

## 决策

**1. 调度与租约的时间一律取注入的 `Clock`。** 架构设计中认领 SQL 写的是 `now()` 与 `now() + interval '30 seconds'`。实现中 `not_before <= :now`、租约到期时间（`lease_expires_at`，由应用计算为当前时间加租约时长）、回收条件 `lease_expires_at < :now`、事件与各表的时间列都以参数绑定，值来自注入的 `Clock`（编码规范「时钟」）。这样租约过期能用可控时钟测试，不用 `sleep`；也避免同一套比较里混用应用时钟与数据库时钟。代价是租约判断依赖各节点的时钟同步：节点之间的偏差必须远小于续租余量（租约 30 秒减续租周期 10 秒），生产环境要求 NTP。

**2. 同节点重新认领的落地方式。** 认领第 1 步在架构设计的条件之外追加 `NOT (t.thread_id = ANY (:excluded))`，`:excluded` 为本节点 `LeaseRegistry` 中仍有条目的线程；第 1 步选中轮次后、提交前，用 `putIfAbsent` 在 `LeaseRegistry` 中预留该线程，提交后激活，回滚或提交失败则取消。只靠 SQL 排除，条目在查询之后才登记时会有窗口；只靠预留，忙碌线程的轮次会因排序靠前被反复选中而阻塞队列。两者一起，本节点同一线程任何时刻最多一个条目。

**3. 租约条件的加锁方式与锁顺序。** 带租约条件的写入（事件、智能体状态）先以 `SELECT ... FOR SHARE` 锁住持有租约的轮次行，再执行写入，而不是把条件写成写入语句里的 `EXISTS` 子查询：READ COMMITTED 下，写入语句在会话行上等锁后重新检查条件时，子查询仍用语句开始时的快照，可能在租约已被回收器收回后照常写入。`FOR SHARE` 与回收器、置回队列的 `UPDATE` 冲突，所以写入事务提交之前租约不会被收回；回收器用 `FOR UPDATE SKIP LOCKED`，跳过正在被写入的轮次，下个周期再处理。同一轮次的多个写入方（主线程与子线程）之间互不阻塞。全部事务按"先 `rt.turns`，再 `rt.tenant_concurrency`，再 `rt.sessions`"加锁：认领、回收、置回队列、结束轮次、带租约的事件写入都遵守。API 在同一事务里写 `user.*` 事件并入队时，必须先入队、再写事件，否则与回收同一会话的轮次相互等待，由数据库的死锁检测中止其中一方；轮次输入与收件箱需要的事件 ID 由 T07 改为调用方先生成、随批次传入写入入口（T05 的写入入口自己生成事件 ID）。

**4. 事件内容与轮次输入的 JSON 约定。** `session_events.data` 与 `turn_inputs.payload` 由 runtime 的 `EngineJson` 编解码，在 `common.json`（snake_case、RFC 3339 UTC）之上：枚举写成小写的常量名，与 engine-spi 各枚举的 `value()` 一致（单元测试遍历事件与输入可达的全部枚举核对）；`MessageContent` 带判别字段 `type`，取值 `text`、`image`、`file`；没有字段的事件写成 `{}`。`data` 不含事件类型（由 `session_events.type` 给出），`payload` 不含轮次类型（由 `turns.kind` 给出）。读取时忽略未知字段。T07 的 OpenAPI 中事件 `data` 的 schema 以此为准。

**5. 状态事件在写入事务中推进会话与线程状态。** 事件写入入口（`SessionEventWriter`）插入 `session.status_*` 事件时，在同一事务中把 `rt.sessions.status` 改为对应状态，事件带线程时线程状态同步（终止事件只改会话）；`session.thread_status_running`、`session.thread_status_idle` 改事件内容中的子线程。会话状态因此不会与事件日志分叉，回收器发出 `session.status_rescheduled` 时会话随之进入 `rescheduled`。

**6. 轮次离开 `running` 时保留最近的持有者与 epoch。** 置回队列与结束轮次时清空 `lease_expires_at`，保留 `lease_owner`（最近一次持有者，便于排查）与 `lease_epoch`（失败那次执行的 epoch）。下次认领时 epoch 加一，所以恢复认领时失败那次的 epoch 等于新 epoch 减一，T06 据此与 `content_epoch` 比较，不需要额外的列。置回队列时 `not_before` 设为当前时间，立即可被认领。租约条件总是同时要求 `status = 'running'`。

**7. 新租户的默认并发上限为 20。** 架构设计规定计数行的 `max_running` 在没有租户配额时取全局默认值，没有给出数值。M0 取 20（`meridian.runtime.dispatch.default-tenant-max-running`）：单个 runtime Pod 的目标是 300 个并发轮次，20 能让单租户的突发不占满一个节点，也足够开发与测试。T14a 起改为取租户配额。

**8. 续租失败阈值从上次成功续租起算。** "续租连续失败超过 15 秒"按"距上次成功续租（或认领）超过 15 秒仍续不上"判断，在下一次续租尝试时检查；默认周期下等于连续两次失败，执行方在租约到期（30 秒）之前停下。续租更新 0 行时租约确定已失去，立即通知执行方。

**9. 节点 ID 每个进程不同。** 默认取环境变量 `HOSTNAME`（Kubernetes 中为 Pod 名）加 8 位随机后缀，只含字母、数字、点、下划线与短横线，可直接用于中断频道 `node:{lease_owner}`。容器在同一个 Pod 内重启时，新进程不会把上一个进程留下的轮次当成自己的。

**10. 释放租户名额时计数不会变成负数。** 释放语句带 `running > 0` 条件；更新 0 行说明计数与轮次不一致，记录 ERROR 日志，不阻塞置回队列与结束轮次。表上另有 `CHECK (running >= 0)` 兜底。

**11. 核心表的补充列。** 为避免频繁改表，迁移在架构设计的关键列之外加入后续任务确定需要的列：`sessions` 的 `end_user_attributes`、`metadata`、`custom_tools`（T07 的创建请求）、`last_activity_at` 与 `events_archive_key`、`events_archived_at`（T17a 的事件归档）、`terminated_at`；`turns` 的 `session_id`、`claimed_at`、`finished_at`；`tool_invocations` 的 `session_id`、`lease_epoch`（发起调用的那次执行）；`pending_actions` 的 `session_id`。`session_events` 的唯一约束 `(session_id, id)` 包含分区键。

## 影响

- 架构设计：「认领」的 SQL 改为绑定 `:now` 并追加本节点持有线程的排除条件；「租约」补充加锁方式、锁顺序与续租失败阈值的起算点；「租户并发计数行」写明默认值；「状态机」写明状态随事件推进。版本 v1.4。
- 代码：`meridian-runtime` 的 `dispatch`、`stream`、`session` 上下文与 `V0001__runtime_core.sql`；engine-spi 不变。
- T06：Worker 结束轮次、写终态事件、写 outbox、插入下一轮放在一个事务里，遵守锁顺序；恢复认领时失败的 epoch 取 `epoch - 1`。T07：事件 `data` 的 schema 按第 4 条；入队与写事件的顺序按第 3 条。T14a：计数行的 `max_running` 改取租户配额。
- 风险：节点时钟偏差过大时租约可能被提前回收（被回收的执行写不进任何数据，只是浪费一次执行）；部署要求 NTP。
