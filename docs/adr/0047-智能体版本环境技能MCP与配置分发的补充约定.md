# ADR-0047 智能体版本、环境、技能、MCP 与配置分发的补充约定

| 项 | 内容 |
|---|---|
| 状态 | 已采纳（补充） |
| 日期 | 2026-11-12 |
| 决策人 | T15b |
| 影响的架构设计章节 | 领域模型（ID 规则）、数据架构（control-plane 核心表、跨服务数据流）、代码仓库与模块（端口）、运行时架构（引擎装配、权限判定）、API 设计（资源）、安全架构（授权） |

## 背景

T15b 把 runtime 读开发配置目录的智能体、环境、技能、MCP 与租户设置，改成在 control-plane 中管理、经内部接口与 `config.invalidate` 分发。架构设计规定了表名（`agents`、`agent_versions`（`spec jsonb`，发布后只读）、`environments`（带 `revision`）、`skills`、`skill_versions`、`mcp_servers`）、"会话绑定版本，修改定义不影响运行中的会话"、引擎实例按 `(agent_version_id, environment_id, environment_revision)` 缓存、五层权限中的租户与项目策略由 control-plane 下发（ADR-0031），没有规定：

- 智能体规格的格式与校验：控制台编辑、control-plane 保存、runtime 装配用的是不是同一份文档；发布前的草稿怎样存在。
- 已发布的版本引用的 MCP 服务改了端点或凭据、技能出了新版本时，版本还算不算"不可变"；删除被引用的资源怎样处理。
- 技能包的上传格式与存储，MCP 服务的认证方式、工具清单从哪里来、副作用等级标在服务上还是工具上。
- 内部接口的形状、runtime 的缓存与失效、租户提示词随实例缓存时设置变更怎样生效（登记事项 D32）。
- 公开接口 `GET /v1/agents` 在 MVC 服务上的认证（登记事项 D55）、管理接口的角色类别。

## 候选方案

1. **规格的格式**：(a) 草稿是一份"创作格式"（MCP 服务、技能只写 ID），发布时转换成另一份"解析格式"——两份 Schema，控制台的表单校验与 runtime 的契约不一致；(b) 一份 JSON Schema，与 engine-spi 的 `ResolvedAgentSpec` 一一对应，草稿可以省略"发布时填写"的字段，发布时由 control-plane 填入。
2. **已发布版本与被引用资源的关系**：(a) 版本只存引用，解析时联表取 MCP 服务的当前配置——MCP 服务改了，已发布版本的行为跟着变，引擎实例要按 MCP 服务淘汰；(b) 发布时把 MCP 服务的端点、传输、凭据引用与副作用等级写进规格快照——版本真正不可变，MCP 服务的修改在下一次发布时生效。
3. **技能包的上传**：(a) `application/zip`——要处理解压炸弹与路径穿越，幂等指纹要另算；(b) JSON 列出文件（UTF-8 文本）——与 engine-spi 的 `SkillDefinition`（文本文件）一致。
4. **租户设置变更时已装配的实例**：(a) 等实例空闲 30 分钟淘汰；(b) 实例缓存键加入租户设置的版本；(c) 收到通知时淘汰该租户的实例，正在执行的轮次结束后关闭。

## 决策

采用 1(b)、2(b)、3(b)、4(c)。

1. **规格与 Schema。** `meridian-api` 的 `schema/agent-spec.schema.json`（JSON Schema 2020-12）是智能体规格的唯一定义：字段与 `ResolvedAgentSpec` 及其嵌套记录一一对应（snake_case，枚举取小写值，时长为 ISO 8601），标为"发布时填写"的字段（`agent_id`、`agent_version_id`、`name`，MCP 服务的 `name`、`url`、`transport`、`header_secret_ids`、`side_effect`、`tool_side_effects`，技能引用的 `name`）在草稿中可以省略，给出了也会被覆盖。runtime 的 `AgentSpecSchemaTest` 守住一致性：由 Schema 生成的示例通过校验、经 `ResolvedAgentSpec` 往返不变，记录组件与 Schema 字段、平台工具名与枚举取值相同。control-plane 用 networknt `json-schema-validator` 2.0.1 校验（Jackson 2 版：3.x 改用 Jackson 3，但与 AgentScope 2.0.4 带来的 2.0.0 同坐标，不能并存），错误的字段名是 `spec.` 加点号连接的 JSON 路径。智能体名与子智能体名同一格式 `^[a-z][a-z0-9_-]{0,63}$`。
2. **版本的生命周期。** 版本号按智能体从 1 递增；草稿可以修改、删除，保存时按 Schema 校验结构；发布后只读，修改、删除、再次发布都是 409 `agent.version_published`；智能体的当前版本是版本号最大的已发布版本。版本对比按 JSON 指针给出新增、删除、修改，数组按位置比较，草稿也可以参与对比。同一智能体的建版本与发布锁住智能体行串行。
3. **发布时的校验与快照。** 先按 Schema 校验草稿，再写入快照：智能体 ID、版本 ID、智能体名；每个挂载的 MCP 服务的登记配置（服务必须存在，启用的工具必须在探测到的清单中）；每个技能引用的技能名（技能与版本必须存在）。再校验模型（主模型、备用模型、子智能体的模型）存在于本租户目录且是对话模型、知识库存在（`KnowledgeCatalogClient`），最后对快照后的规格再跑一遍 Schema 与 `AgentSpecRules`（Schema 表达不了的规则：名字不重复、声明子智能体要有 `spawn_subagent`、子智能体的工具集是父智能体的子集、子智能体超时在 (0, 600 秒]、前置检索要绑定知识库，与 `ResolvedAgentSpec` 的构造校验一致）。被引用的 MCP 服务与技能以共享锁读取、模型以排他锁读取。
4. **引用与删除。** 发布时把版本（含子智能体）引用的模型、技能、MCP 服务、MCP 请求头凭据、知识库写进 `cp.agent_version_refs`；删除模型、技能、MCP 服务、凭据时，被未删除智能体的已发布版本引用则 409（`catalog.in_use`、`skill.in_use`、`mcp_server.in_use`、`secret.in_use`），`references` 列出 `agent_version`（名称为"智能体名 v版本号"）。智能体、环境、技能是软删除：不能再用于新会话，已发布版本、环境修订、技能版本仍可解析，运行中的会话不受影响；MCP 服务是硬删除（已发布版本持有快照）。
5. **环境。** 档位、规格或白名单变化时修订号加一并追加 `cp.environment_revisions`，只改名字不产生新修订；白名单是域名（小写、去重，`*.` 前缀匹配任意层级子域名，不接受 IP、端口与路径，与 runtime 的 `EgressAllowlist` 一致），至多 100 个。
6. **技能。** 技能包以 JSON 上传（`files: [{path, content}]`，UTF-8 文本）：`SKILL.md` 的 frontmatter 必须有 `name`（`^[a-z0-9][a-z0-9-]{0,63}$`，项目内唯一）与 `description`（至多 1024 个字符），路径为相对路径、不含 `..` 与反斜杠，至多 100 个文件、单个 1 MB、合计 5 MB。文件存对象存储 `cp/skills/{tenant}/{project}/{skill}/v{version}/{path}`，清单（路径、大小、SHA-256）存 `cp.skill_versions`，版本只追加；新版本的 `name` 必须与技能名一致。control-plane 因此需要对象存储配置。
7. **MCP 服务。** 认证是 `header_secret_ids`（请求头名 → 本项目可用的凭据 ID），凭据值是请求头的完整取值（Bearer 令牌写成 `Bearer xxx`），与 `McpServerSpec.headerSecretIds` 一一对应。副作用等级可以标在服务上，也可以按工具单独标注：engine-spi 的 `McpServerSpec` 新增 `toolSideEffects`（工具名 → 等级）与 `sideEffectOf(tool)`，没有标注的工具取服务级等级，再没有时按 `non_idempotent`（ADR-0035 的缺省不变）。登记、修改与 `:probe` 时，control-plane 以自己的身份解析请求头凭据（审计 `secret.resolved`，调用方 `control-plane`），用与 AgentScope 相同版本的 MCP Java SDK（0.17.2）同步客户端连接、握手并逐页列出工具，不跟随重定向、不走系统代理；失败为 400 `mcp_server.probe_failed`，不保存。端点按 `EndpointPolicy` 校验（D32：链路本地与云元数据地址始终拒绝）。按工具标注的副作用只能针对探测到的工具。
8. **租户与项目策略。** 存 `cp.permission_rules`（租户策略的 `project_id` 为空，`source` 为 `policy` 或 `remembered`），同一层中相同的规则（工具、内容、结果）只有一条。管理接口：租户策略按租户设置的类别（`TENANT_READ`、`TENANT_UPDATE`），项目策略按智能体的类别。"记住此决定"（项目级）经内部接口写入，相同的规则返回已有的。runtime 的 `PolicyStorePort` 生产实现读写 control-plane；会话级规则仍在 `rt.permission_rules`，开发实现 `DatabasePolicyStore` 只在 `agent-config.source=file` 时装配。
9. **内部接口（`InternalAgentConfig`、`InternalPermissionRules`、`InternalTenants`，只接受 runtime）。** `POST /internal/v1/agent-versions/{id}:resolve` 与 `POST /internal/v1/agents/{id}:resolve`（当前版本）返回发布时的规格快照、`agent_deleted` 与引用的全部技能版本内容（含子智能体的），runtime 不需要其他查询就能装配引擎，凭据只以 ID 出现；草稿与不存在的版本 404。`GET /internal/v1/environments/{id}[?revision=]`：不带修订号时是当前修订（环境已删除 404），带修订号时环境已删除也返回。`GET /internal/v1/skills/{id}/versions/{version}` 供缓存未命中时单独读取。`GET|POST /internal/v1/projects/{id}/permission-rules`、`GET /internal/v1/tenants/{id}/settings`。解析类接口不按租户过滤，响应带资源的租户与项目，由 runtime 校验与调用方项目一致（与模型目录相同，ADR-0045）。
10. **失效通知。** `config.invalidate` 新增 `agent`（发布、删除，`id` 为智能体）、`environment`（产生新修订、删除）、`skill`、`mcp_server`、`permission_policy`（`id` 为租户或项目）、`tenant_settings`。runtime 的 `ControlPlaneAgentConfigProvider` 缓存：按 ID 的已发布版本、指定修订、技能版本 10 分钟（不可变，只为删除标记与内存），当前版本、当前修订、租户设置 60 秒；`ControlPlanePolicyStore` 按项目缓存 60 秒；收到通知立即淘汰。`skill`、`mcp_server` 不需要 runtime 处理（版本不可变、MCP 有快照）。绑定了 `PlatformContext` 时资源必须属于其中的项目，否则与不存在相同（D18）；出网授权这类系统路径没有上下文，不校验。创建会话时按版本 ID 固定版本走 `AgentConfigProvider.agentVersionForNewSession`，智能体已删除时 404。control-plane 读不到时抛可重试的 `ConfigUnavailableException`。
11. **租户设置变更淘汰实例（D32）。** engine-spi 的 `AgentEngine` 新增 `evictAgentVersions(Set<String>)`：从实例缓存移除这些版本的实例（含子智能体），空闲的立即关闭，正在执行的本轮结束后关闭。runtime 记下"智能体版本 → 租户"（空闲 2 小时过期，长于实例的 30 分钟），收到 `tenant_settings` 时据此淘汰。联网搜索后端的端点在 runtime 读取时按地址策略再校验一次，不允许时按未配置处理（D61）；control-plane 写入时另校验凭据存在且是租户级。
12. **公开接口。** `GET /v1/agents`、`GET /v1/agents/{id}` 由 control-plane 提供，只给出本项目发布过版本的智能体与当前版本，需要 `sessions:read`。认证与限流抽成 `meridian-security` 的 `PublicApiAdmission`，WebFlux 的 `ApiKeyWebFilter` 与新增的 MVC `ApiKeyFilter` 共用（D55）；control-plane 提供进程内的 `ApiKeyResolver`（直接查库，吊销立即生效）与 `ProjectAccessResolver`。runtime 只生成自己的公开标签。
13. **授权。** 新增操作类别 `AGENT_READ`、`AGENT_WRITE`（项目级），覆盖智能体与版本、环境、技能、MCP 服务、项目策略："项目开发者管理本项目的智能体、环境、技能"——开发者与所有者有写，租户管理员与项目观察者只读，审批人没有。
14. **其他。** ID 前缀 `prl`（权限规则）。知识库的存在性在 T18 之前由 `ConfiguredKnowledgeCatalog` 判定（配置 `meridian.control-plane.knowledge.dev-knowledge-base-ids` 中的 ID），`TODO(T18)` 换成 knowledge 服务。runtime 的来源 `meridian.runtime.agent-config.source`：`control-plane`（默认）或 `file`（开发配置目录，只允许 dev、test，`dev` 默认 `file`，与 `catalog-source` 相同）。

## 影响

- 架构设计：ID 规则加 `prl`；control-plane 核心表加 `agent_version_refs`、`environment_revisions`、`permission_rules`；跨服务数据流的 `config.invalidate` 类型；端口表的 `AgentEngine.evictAgentVersions`；权限判定中 T15b 的落地；资源表中智能体接口由 control-plane 提供；授权的操作类别。
- `McpServerSpec` 多一个组件（保留原 7 参构造函数），`AgentEngine` 多一个方法（唯一实现 `AgentScopeEngine`）。
- control-plane 依赖新增 networknt `json-schema-validator`、MCP Java SDK，并需要对象存储；`meridian-test-support` 新增进程内 MCP 服务（嵌入式 Tomcat 加 SDK 的 Servlet 传输）。
- 已发布版本持有 MCP 服务的快照：MCP 服务改了端点、凭据或副作用等级，要重新发布智能体才生效；删除凭据会被引用它的 MCP 服务与已发布版本挡住，已删除智能体的版本不再算引用方（它的运行中会话可能因此失败，与模型的删除相同）。
