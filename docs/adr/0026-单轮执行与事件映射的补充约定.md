## 背景

T04 实现 `AgentScopeEngine`、事件映射与 `FencedAgentStateStore`。逐项核对 AgentScope 2.0.4 源码后，有几处架构设计没有写到、但落实"每轮恰好一个终态""事件映射"必须定下来的细节。它们影响 runtime 的 Worker（T06）、API 的事件取值（T07）和模型层（T09a），所以记录在这里。

## 决策

**1. 可重试错误的终态是 `session.status_rescheduled`。** 架构设计规定可重试的错误（限流等待超时、可重试的供应商错误）产生 `session.error`（`retry_status=retryable`）并置回队列，又规定每轮必须以 idle、requires_action、rescheduled 之一结束。轮次回到 `queued`、等待其他 Worker 认领，对应的会话状态是 rescheduled。所以内核输出 `session.error`（`retryable`）后，以 `session.status_rescheduled` 结束，原因新增取值 `retryable_error`（`RescheduleReason.RETRYABLE_ERROR`）。恢复次数是否用尽（`recovery_attempt` 达到 2）仍由 Worker 在认领时判断，内核不输出 `exhausted`。

**2. 决定终态的异常类型放在 `meridian-engine-spi` 的 `error` 包。** `BudgetExceededException`（`model.budget_exceeded`，以 `budget_exceeded` 结束）、`RetryableTurnException`（可重试错误的基类）、`RateLimitTimeoutException`（`model.rate_limit_timeout`），错误码枚举 `ModelErrorCode`。它们由 runtime 的 `ModelGateway` 实现与内核的 `RoutedModel` 抛出，两者都依赖 engine-spi。T09a 判定可重试的供应商错误时继承 `RetryableTurnException`。其他平台异常带自己的错误码与说明；未预期的异常用 `internal.error`，说明为"本轮执行失败"，不暴露内部信息。

**3. 内核自己发现租约丢失时不输出事件。** `LeaseGuardMiddleware` 或状态写入抛出 `LeaseLostException` 时，本节点已不拥有这一轮：事件写入带同样的租约条件，写不进去；终态由回收器（`lease_expired`）或新的认领者给出。内核不输出任何事件，以 `LeaseLostException` 结束事件流，Worker 据此放弃本轮。这与"失去租约时不写入任何数据"一致，也保证这一轮在会话事件中仍然只有一个终态。

**4. `agent.tool_use` 在所在模型调用结束时输出。** 2.0.4 的 `ModelCallBlockLifecycle` 遇到新的工具调用 ID 时，先对此前所有调用发出 `TOOL_CALL_END`；并行调用的入参片段交错到达时，同一个 ID 会多次收到 `TOOL_CALL_START` 与 `TOOL_CALL_END`，第一次 `TOOL_CALL_END` 时入参还不完整。每次模型调用结束时 2.0.4 先补发全部 `TOOL_CALL_END` 再发 `MODEL_CALL_END`，所以适配层按工具调用 ID 累积片段，在 `MODEL_CALL_END` 时（即每个调用最后一次 `TOOL_CALL_END` 之后）按首次出现的顺序输出 `agent.tool_use`，流上的 `event_start` 每个调用只出现一次。

**5. 块 ID 带上 `replyId`。** 2.0.4 的文本与思考块 ID 在每次模型调用内从 `text`、`text-2` 重新编号。平台事件的块 ID 取 `{replyId}:{blockId}`，避免同一轮多次推理的块相撞；`span.model_request_*` 的 `request_id` 取 `replyId`。

**6. 工具结果块在流上有 `event_start`。** `TOOL_RESULT_START` 输出 `event_start`（块 ID 为工具调用 ID，种类 `tool_result`），与 `StreamEvent` 中"工具结果块取工具调用 ID"的定义一致；增量仍是 `event_delta`。

**7. 自定义工具只以 `agent.custom_tool_use` 出现。** 自定义工具的 `TOOL_CALL_END` 不输出 `agent.tool_use`；它在 Toolkit 中挂起时 2.0.4 发出状态为 `RUNNING` 的 `TOOL_RESULT_END`，这一条不输出（结果由业务方经 `user.custom_tool_result` 回传）；`REQUIRE_EXTERNAL_EXECUTION` 按事件映射表输出 `agent.custom_tool_use` 与 `custom_tool_result` 动作。

**8. 平台中间件的停止原因记在 `PlatformStopRequest`。** 架构设计规定以 `*_STOP_REQUESTED` 结束时"平台中间件发起时，取它记录的原因"。2.0.4 并不总把 `RequestStopEvent` 发布到事件流上（"全部工具被拒绝"路径只合并进 `GenerateReason`），所以引擎每轮在 `RuntimeContext` 中放一个 `PlatformStopRequest`，平台中间件经 `PlatformStopRequest.request(ctx, reason)` 记录原因并发出停止事件，事件映射在流结束时读取；第一次请求生效。

**9. 审批批准的调用带入参原文。** 2.0.4 批准时用 `ConfirmResult.toolCall` 整体替换原调用，而 `ToolExecutor` 按 `ToolUseBlock.content`（入参 JSON 原文）做 schema 校验，`content` 为空会被判为参数缺失。翻译层构造的 `ToolUseBlock` 同时带 `input` 与其 JSON 原文。

**10. 执行一轮的资源在终态之前归还。** 实例租用、执行登记、状态缓存清理用 `usingWhen` 在终态事件之前完成；订阅在准备阶段（虚拟线程上装配与安装权限）被取消时，由资源槽在准备完成后自行归还，避免实例与执行登记泄漏。调用被 AgentScope 受理之前收到的中断会被 2.0.4 静默丢弃，引擎在看到第一个非 `AGENT_START` 事件时补发一次。

## 候选方案

- 第 1 条：只输出 `session.error` 不输出终态，违反"每轮恰好一个终态"；输出 `session.status_idle(error)` 会让会话错误地回到空闲，而轮次实际在排队。
- 第 3 条：补发 `session.status_rescheduled(lease_expired)`。它写不进数据库，即使写进去也会与回收器的事件重复，不采纳。
- 第 4 条：在第一次 `TOOL_CALL_END` 输出，交错到达时入参不完整；从 `onActing` 的入参取完整调用，需要把中间件与映射器耦合，且审批与拒绝路径不经过执行。
- 第 8 条：按 `RequestStopEvent.reason` 的前缀识别平台停止，在"全部工具被拒绝"路径上看不到事件。

## 影响

- 架构设计：「状态机」的 running → rescheduled 增加"可重试错误"；"置回队列的三种情况"中可重试错误一行补上 `session.status_rescheduled`；「事件映射」表注明第 4、6、7 条与租约丢失；「平台中间件」表注明 `OtelTracingMiddleware` 由 `PlatformTracingMiddleware` 装配；「包结构」增加 `turn/`。版本 v1.3。
- `meridian-engine-spi`：新增 `error` 包；`SessionEvent.RescheduleReason` 新增 `retryable_error`；`AgentEngine.runTurn` 的注释写明租约丢失时的行为。
- T06 的 Worker：`rescheduled` 按原因区分 `recovery_attempt` 是否加一（`node_shutdown` 不变，`retryable_error` 加一）；收到 `LeaseLostException` 时放弃本轮、不写事件。T07 的 API 文档列出 `retryable_error`。T09a 的可重试供应商错误继承 `RetryableTurnException`。
