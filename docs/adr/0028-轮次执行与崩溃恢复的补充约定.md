# ADR-0028 轮次执行与崩溃恢复的补充约定

| 项 | 内容 |
|---|---|
| 状态 | 已采纳（补充） |
| 日期 | 2026-11-07 |
| 决策人 | T06 执行会话 |
| 影响的架构设计章节 | 「核心表」、「平台中间件」、「一轮执行的生命周期」、「消息投递」、「崩溃恢复」、「可观测性」（只补充，不改既有条款） |

## 背景

T06 把调度与内核接起来：Worker 认领、执行、写事件、结束轮次，以及崩溃恢复、批次级 checkpoint（P3）和优雅下线。按架构设计落实时发现几处没有写到的细节，其中第 1 条是一个真实的缺口：

- `rt.turns.lease_epoch` 每个新轮次从 0 开始，认领时加一。`agent_states.content_epoch` 只记 epoch，不记是哪一轮写的。上一轮 epoch 1 正常结束（`content_epoch = 1`），下一轮 epoch 1 被强杀、没有写入内容，回收后新认领者比较 `content_epoch (1)` 与失败的 epoch `(1)`，二者"相等"，会判为"已保存中途状态"而不重放输入，丢掉用户消息。`LeaseFencingIT.contentWritesRecordTheirTurnBecauseEpochsRestartEveryTurn` 复现了这个碰撞。
- 一轮可能执行不止两次（例如先优雅下线、续跑时又被强杀）。此时最近的内容写入来自更早的一次执行，只比较"失败那次"的 epoch 会判为"未写入"并重放输入，同样会重复用户消息。

其余各条是落实生命周期、恢复、下线、事件扇出时必须定下来、又会影响 T07、T08、T10a、T16 的约定。

## 候选方案

- 第 1 条：让 `lease_epoch` 在线程内单调（新轮次从该线程历史最大值起算）。只改入队 SQL，但仍要用 `claim_count` 推算本轮的第一个 epoch，而且 epoch 的含义从"本轮第几次执行"变成"线程内第几次执行"，影响 ADR-0027 第 6 条的推导。不采纳。
- 第 1 条（采纳）：状态写入时同时记下持有租约的轮次 `content_turn_id`。仓储在写入事务里本来就以 `FOR SHARE` 锁住了持有租约的轮次行，轮次 ID 现成可得，端口签名不变。
- 第 6 条：Worker 写完一批事件后自己 XADD。每个写入路径（Worker、回收器、置回队列、内核端口）都要记得发布，容易漏；改为在唯一的写入入口提交后发布。
- 第 10 条：在 runtime 里为四个内核提供者写临时实现，让生产环境现在就能装配内核。属于桩代码，不采纳。

## 决策

**1. 状态内容写入记录所属轮次，恢复按"本轮的内容写入"判定。** 新增列 `agent_states.content_turn_id`（迁移 `V0002`），内容写入时更新为持有租约的轮次（子线程写入为父轮次），权限安装写入保留原值。恢复认领时查询本轮在线程状态中最近一次内容写入的 epoch（`contentEpochOfTurn`），按 `RecoveryPlanner` 判定：

| 本轮的内容写入 | 恢复方式 | 重新投递失败那次执行消费的 steer |
|---|---|---|
| 没有 | 重放 `turn_inputs` 中的完整输入（`REPLAY_INPUT`） | 是 |
| 有，来自失败那次执行 | `RecoveryOnly`（`RESUME_SAVED_STATE`） | 否 |
| 有，来自更早的一次执行 | `RecoveryOnly` | 是 |

只执行过一次的轮次，结果与架构设计"比较 `content_epoch` 与失败的 `lease_epoch`"完全相同；多次执行与跨轮碰撞时，按"本轮内容是否写入、写在哪次执行"判断，保证不重复用户消息、不丢 steer。

**2. 恢复认领的判断与恢复次数。** 恢复认领是"本轮此前执行过"，即 `epoch > 1`，不用 `recovery_attempt > 0`：优雅下线置回时恢复次数不变，但续跑同样要走恢复判定（`ClaimedTurn.isRecovery` 改为按 epoch）。engine-spi 的 `RecoveryOrigin.recoveryAttempt` 相应允许 0。认领时 `recovery_attempt` 已达 2，本轮不再执行：写 `session.error`（`turn.recovery_exhausted`，`retry_status=exhausted`）与 `session.status_idle`（`error`），轮次以 `failed` 结束——即一轮最多执行原始一次加一次恢复。

**3. 批次级 checkpoint（P3 通过，默认开启）。** `BatchCheckpointMiddleware` 在"一批工具执行完之后的下一次推理之前"调用 `saveAgentState(ctx)`：2.0.4 在 `onActing` 的事件流结束之后才把工具结果写进 `AgentState`，此时整批结果都在上下文里，tool_use 与 tool_result 一一配对。配置 `meridian.runtime.worker.batch-checkpoint`（默认 `true`）可关闭。中间件顺序 `RecoveryNote(90)` → `BatchCheckpoint(80)`；T08 的 `SteerMiddleware` 必须排在 `BatchCheckpoint` 之外，否则一次推理前注入的 steer 不在该次 checkpoint 中，强杀后会丢。代价：每批工具多一次状态写入。

**4. 恢复说明。** `RecoveryNoteMiddleware`（`onReasoning`）在恢复轮第一次推理前把说明作为一条用户消息追加到推理输入与 `AgentState`；说明经 `RuntimeContext` 传入，不走调用入参。说明列出此前各次执行中已成功的调用（附结果摘要，上限 1000 字符）与仍为 `running` 的调用（状态未知）；失败、被拒绝、被中断的调用状态已知，不列出。结果摘要先取已持久化的 `agent.tool_result`（或 MCP 结果）事件，取不到时取账本的 `result_ref`；强杀发生在结果事件写库之前时只能取账本，所以 T10a 的平台工具基类在记录结束时应写入结果引用（至少 `non_idempotent` 工具）。

**5. 恢复确认。** 状态未知的 `non_idempotent` 调用，每个创建一个 `recovery_confirmation` 待处理动作，`payload` 除工具调用外带 `invocation_id`、`idempotency_key`、`side_effect`、`failed_epoch`、`recovery_mode`（`replay_input` 或 `resume_saved_state`），本轮以 `awaiting_action` 结束，会话转为 `requires_action`。回应由 T08 处理：`recovery_mode = replay_input` 时状态里没有本轮的输入，T08 生成恢复轮时需要重放原轮输入（附恢复说明），只生成 `RecoveryOnly` 会丢掉用户消息（登记事项 D13）。

**6. 事件扇出在唯一写入入口提交后进行。** `SessionEventWriter` 在事务提交后把写入的事件 XADD 到 `ev:{session_id}`（不等待），回滚的事务不发布；只在流上的事件由 Worker 与 `DatabaseEventSink` 直接发布。条目字段：`type`、`seq`（只有持久化事件有）、`envelope`（与 API 一致的事件信封 JSON）。Stream 按 `MAXLEN ~ 1000` 裁剪、最后一次写入 1 小时后过期，只做实时扇出，更早的事件由 SSE 从数据库补发。XADD 失败只记指标 `meridian_event_publish_failures_total`。命令都在调用线程上按顺序发出：不在前一条命令完成的回调（Netty 事件循环）上发下一条，同一写入方的条目顺序与 `seq` 一致；不同写入方的条目可能交错，SSE 按 `seq` 去重与回补（T07）。

**7. 轮次结束的事务。** 以空闲结束：线程咨询锁 → 结束轮次（租约条件即 fencing）与租户并发计数减一 → 收件箱中待投递的消息（queue，以及没来得及注入、降级为 queue 的 steer）合并成下一轮并入队 → 写终态事件 → 写 outbox（主题 `audit`，动作 `turn.finished`，格式由 T16 定稿）。以 `requires_action` 结束：轮次进入 `awaiting_action`，内核给出的动作写入 `pending_actions`（截止时间默认 30 分钟，`meridian.runtime.worker.pending-action-timeout`），消息留在收件箱。以 `rescheduled` 结束：按原因置回队列（`retryable_error` 加一次恢复次数，`node_shutdown` 不加）。停止原因到轮次状态：`interrupted` → `interrupted`，`error` → `failed`，其余 → `completed`。

**8. 消息入箱与轮次结束按线程串行。** 两边都先取 `pg_advisory_xact_lock(hashtextextended(thread_id, 0))`（`ThreadLockRepository`）。否则会丢消息：API 插入轮次时线程仍有执行中的轮次（插入为空操作），Worker 结束轮次时又看不到这条尚未提交的消息。回收器不取这把锁，加锁顺序仍按 ADR-0027 第 3 条，不会形成死锁。T07 写 `user.message` 的事务必须先取这把锁（登记事项 D12）。

**9. 消息消费事件与合并。** `session.message_consumed` 在一轮第一次执行开始时与 `session.status_running` 一起写入（恢复续跑不再写）。合并进下一轮的消息记 `consumed_turn_id` 为下一轮、`consumed_epoch` 为空（它们随输入重放）；只有执行中经 steer 注入的消息记 `consumed_epoch`。

**10. 内核装配写成自动配置。** `EngineAutoConfiguration` 在模型工厂、工具、文件系统、技能仓库四个提供者都存在时才装配 `AgentScopeEngine` 与 Worker 的后台循环。T06 时生产环境还没有这些提供者（T09a、T10a 交付），runtime 照常启动、不认领轮次；测试与后续任务提供它们后即生效。对象存储成为 runtime 的必需配置（`BlobStorePort` 的键为 `rt/{tenant_id}/{session_id}/blobs/{ulid}`，删除会话时按前缀清除）。智能体配置的来源是 runtime 内部接口 `AgentConfigProvider`，T06 的实现从 `dev-config/agents/` 读取 YAML。

**11. Worker 生命周期。** `TurnWorkerLifecycle` 的阶段为 `SmartLifecycle.DEFAULT_PHASE`（最先停止），续租、回收、队列深度任务的阶段更小（后停止），下线等待执行结束期间仍在续租，恢复次数不会因为租约过期而增加。下线等待 60 秒（`shutdown-timeout`），本节点并发上限 300（`max-concurrent-turns`，单个 Pod 的目标并发轮次数）。部署的 `terminationGracePeriodSeconds` 必须大于下线等待（T28）。

**12. jsonb 写入替换 NUL。** `JdbcValues.jsonb` 把 JSON 中的 NUL（转义序列与原始字符）替换为 U+FFFD，所有 jsonb 列（事件、状态、输入、账本、待处理动作、outbox）都经过它（登记事项 D11）。

**13. 指标命名。** Micrometer 名用点分隔（例如 `meridian.turns`），导出到 Prometheus 时按类型加后缀，与架构设计「可观测性」表一致（`meridian_turns_total`、`meridian_turn_duration_seconds` 等）。`meridian_turns_total` 的 `status` 为轮次状态或 `queued`（置回队列）；排队时长只记第一次认领。

## 影响

- 架构设计：「核心表」`agent_states` 增加 `content_turn_id`；「崩溃恢复」第 2 步写明按本轮的内容写入判定（含表）、批次级 checkpoint 已启用、恢复次数用尽的含义；「平台中间件」增加 `BatchCheckpointMiddleware` 一行；「一轮执行的生命周期」写明结束事务的顺序与线程咨询锁；「可观测性」增加 `meridian_event_publish_failures_total`。版本 v1.5。
- 代码：`meridian-persistence`（`JdbcValues`、`PeriodicJob` 阶段、`ReactiveRedisMessaging` 的有界发布）；`meridian-engine-spi`（`RecoveryOrigin`）；`meridian-engine-agentscope`（两个中间件）；`meridian-runtime`（`session`、`delivery`、`tooling`、`approval`、`stream`、`config`，迁移 `V0002`）。
- T07：写 `user.message` 的事务先取线程咨询锁（D12）；SSE 按本 ADR 第 6 条的条目字段读取 `ev:{session_id}`。T08：`SteerMiddleware` 的顺序在 `BatchCheckpointMiddleware` 之外；`recovery_confirmation` 回应在 `replay_input` 模式下重放原轮输入（D13）。T10a：平台工具结束时把结果引用写进账本（D14）。T16：`turn.finished` 审计消息的格式。T28：`terminationGracePeriodSeconds` 大于 60 秒。
- 风险：Redis 慢时未完成的 XADD 订阅受 2 秒超时约束；节点下线等待最长 60 秒（AgentScope 在 45 秒时强制中断），部署要留足宽限期。
