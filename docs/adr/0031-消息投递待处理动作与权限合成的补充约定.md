## 背景

T08 落地消息投递、待处理动作与权限合成。架构设计规定了投递表、动作表、五层规则与两处改写，按 AgentScope 2.0.4 源码落实时有几处没有写到、又会被 T10a、T12a、T13、T15b、T16 依赖的细节，其中两处是真实的缺口：

- **平凡权限上下文。** 2.0.4 的 `ReActAgent.evaluatePermissions` 在权限上下文"平凡"（`DEFAULT` 模式、没有任何规则、没有工作目录）时不走 `PermissionEngine`，除工具自检的 ask 外一律放行。平台每轮都注入平台安全规则，上下文因此永远不平凡：`DEFAULT` 模式下没有命中 allow 的调用一律 ask，这正是架构设计"判定顺序……默认 ask"的含义，但也意味着智能体必须显式放行它的工具，会话声明的自定义工具也会先被要求确认，而不是挂起等待业务方的结果。
- **恢复确认与重放。** 架构设计写"`recovery_confirmation` 的回应一律生成 `RecoveryOnly` 轮"。恢复方式为 `replay_input`（进程被强杀，状态里没有本轮的输入）时，`RecoveryOnly` 会丢掉用户消息（登记事项 D13）。

其余各条是落实中断、steer、恢复轮、超时、审计时必须定下来的约定。

## 候选方案

**等待回应时被中断的"恢复轮后停止"**

- A：给恢复轮写上 `interrupt_requested_at`，认领后按普通中断送达（续租回调调用 `AgentEngine.interrupt`）。2.0.4 在调用被受理、看到第一个事件之后才响应中断；`RecoveryOnly` 轮的第一个事件就是模型调用开始，中断可能在模型调用之后才送达，脚本化模型的回应已被消费，结果不确定。
- B（采纳）：同样写上 `interrupt_requested_at`（数据库仍是事实来源，恢复认领时同样生效），内核在 `RuntimeContext` 中放一个标记，平台中间件 `InterruptCheckpointMiddleware` 在第一次推理前以 `InterruptedException` 结束推理。2.0.4 的推理入口把它当作用户中断走 `handleInterrupt`：补齐悬空的工具结果、追加中断说明、保存状态，以 `INTERRUPTED` 结束。本轮的输入（拒绝结果、错误结果、恢复说明）已在上下文中，不再调用模型。
- C：中间件发出 `RequestStopEvent` 而不调用下游。2.0.4 在没有模型输出时 `buildFinalMessage()` 为空，推理返回空结果，不采纳。

**会话声明的自定义工具**

- A：智能体配置里逐个放行。自定义工具是会话级的，智能体版本发布时不知道它们。
- B（采纳）：会话层为每个自定义工具加一条整工具 allow。声明就是业务方的授权；上层的 deny、ask 仍然优先，管理员可以收紧。

**无人值守会话的兜底**

- A：照常产生待处理动作，立刻以平台的结论回应。会话会短暂进入 `requires_action`，Webhook 与 SSE 收到调用方无法回应的动作，与"不产生待处理动作"不符。
- B（采纳）：本轮以 `session.status_idle(tools_denied)` 结束，同一事务中入队一个 `confirmations` 恢复轮，输入是对全部待确认调用的拒绝结果；收件箱中的消息留到恢复轮结束。与"本轮结束时合并收件箱成下一轮"相同，空闲之后紧接着下一轮。

## 决策

**1. 权限合成。** 结果是五层规则的并集，按层从高到低排列（平台安全规则、租户、项目、智能体版本、会话），每条规则带所属层，相同（工具、内容、结果）的规则只保留层最高的一条。冲突按 `PermissionEngine` 的原生顺序裁决（deny → ask → 工具自检 → allow → BYPASS → 默认 ask），所以低层只能收紧，不能放开高层的 deny 与 ask；"记住此决定"写入的 allow 只对没有命中 deny、ask 的调用生效。租户、项目、会话三层只有规则；模式取智能体配置，`unattended` 会话与子线程固定为 `DONT_ASK` 并把全部 ask 改写为 deny，`unattended` 会话额外 deny `plan_enter`。实现为 runtime 的纯函数 `approval.domain.PermissionSynthesizer`。

**2. 平台安全规则。** `write_file`、`edit_file` 对 `AGENTS.md`、`skills/**`、`subagents/**`、`tools.json`、`MEMORY.md` deny；`read_file`、`grep_files` 对凭据类文件 deny（`**/.env`、`**/.env.*`、`**/*.pem`、`**/*.key`、`**/*.p12`、`**/*.pfx`、`**/*.jks`、`**/id_rsa*`、`**/id_ecdsa*`、`**/id_ed25519*`、`**/.ssh/**`、`**/.aws/credentials`、`**/.netrc`、`**/.npmrc`、`**/.pypirc`、`**/.git-credentials`、`**/.docker/config.json`、`**/.kube/config`）。规则内容是相对工作区根的路径 glob，`**` 匹配零或多级目录（`**/.env` 也匹配根目录的 `.env`），T10a 的文件工具 `matchRule` 必须按此解释。`bash` 只有命令前缀规则，沙箱中的保护由 T12a 负责。

**3. 平凡权限上下文与自定义工具。** 平台安全规则使权限上下文永远不平凡（见背景），智能体版本必须显式放行它的工具或选择放行的模式；会话声明的自定义工具在会话层各有一条整工具 allow。

**4. 子线程的权限。** 轮次开始时为智能体配置的每个子智能体预先合成，放进 `TurnContext.subagentPolicies`：`DONT_ASK`；父智能体合成结果与子智能体配置中的 deny 全部保留、ask 全部改写为 deny；allow 取父智能体中工具属于子智能体工具集的 allow，子智能体配置自带的 allow 只在被父智能体的 allow 覆盖（同一工具，父规则不带内容或内容相同）时保留。

**5. "记住此决定"。** 对被确认的工具记一条整工具规则，批准记 allow、拒绝记 deny；`remember_scope=session` 写入 `rt.permission_rules` 的会话层，`project` 经 runtime 内部端口 `PolicyStorePort` 写入项目层（开发实现同样是 `rt.permission_rules`，T15b 迁到 control-plane）。批准时规则同时随 `ConfirmResult.rules` 在本轮立即生效。工具的内容级建议（命令前缀、路径）在平台工具实现 `generateSuggestions` 之后由内核随动作带出（登记事项 D21）。租户层规则在 T15b 之前没有写入接口。

**6. 中断。** 节点频道 `node:{lease_owner}` 的消息是线程 ID，节点收到后立即对该线程续租一次（`LeaseRenewer.renewThread`），从数据库读出中断请求或发现租约已失去；通知丢失时由每 10 秒的续租兜底。中断按本批到达时主线程的状态处理：执行中写 `interrupt_requested_at` 并通知；排队中的消息轮置为 `cancelled`（`stop_reason=interrupted`），写 `session.status_idle(interrupted)`，收件箱中尚未投递的消息与本批随后的消息合成下一轮；排队中的恢复轮（`confirmations`、`custom_tool_results`、`recovery`）不取消，改为写 `interrupt_requested_at`，执行时把结论写进上下文后停止，否则状态里待确认的调用没有结论；等待回应时对全部待处理动作生成拒绝结论（恢复确认视为 skip），生成带中断请求的恢复轮。认领时带中断请求的轮次，`TurnContext.interruptRequested` 为真，按候选方案 B 在第一次推理前停止。删除会话取消执行中的轮次后同样通知持有租约的节点。

**7. steer。** `SteerMiddleware`（order 85）在 `InterruptCheckpointMiddleware`（88）之内、`BatchCheckpointMiddleware`（80）之外，只挂在主智能体上。`InboxPort.consumeSteer` 在同一事务中标记消费（`consumed_turn_id`、`consumed_epoch`）并写 `session.message_consumed`。等待回应时到达的 steer 以 queue 写入收件箱。

**8. 待处理动作的结论与恢复轮。** 新增列 `pending_actions.response`（结论 JSON：来源 `caller`、`timeout`、`interrupt`、`unattended` 与按类型的内容）与 `consumed_turn_id`（交出结论的恢复轮），迁移 `V0004`。一轮的全部动作都有结论时，等待回应的轮次结束为 `completed`，同一事务中入队恢复轮；同批既有确认类动作又有自定义工具时先交出确认，自定义工具的结论留着，确认轮再次停在 `TOOL_SUSPENDED` 时平台直接交出（2.0.4 中待确认的调用会让整批工具都不执行，自定义工具在确认之后才挂起，所以实际总是先确认、后工具结果）。`recovery_confirmation`：恢复说明在恢复认领时生成并随动作保存，回应后把被确认的调用标为 `RETRIED` 或 `SKIPPED`；恢复方式为 `resume_saved_state` 时生成 `RecoveryOnly`，为 `replay_input` 时重放原轮输入并附说明（D13）。`retry` 在恢复轮第一次执行、调用内核之前由 Worker 经 `AgentEngine.retryToolCall` 用原幂等键重新执行，结果摘要写进说明；内核把原幂等键以 `ToolRetryContext` 放进 `RuntimeContext`，T10a 的工具基类记账时优先使用它。

**9. 无人值守会话的兜底。** 按候选方案 B。同一 `requires_action` 中还有自定义工具时（2.0.4 不会出现），确认类动作以 `unattended` 结论写入，自定义工具照常等待业务方。

**10. 超时。** 每个节点每 10 秒扫描一次（`approval.app.PendingActionTimeouts`，仓储在 `approval.infra.system`）。动作行以 `SKIP LOCKED` 锁住，同一动作只被一个节点处理；随后不等待地尝试取线程咨询锁（`pg_try_advisory_xact_lock`），拿不到就留到下次：发送事件与结束轮次的事务先取咨询锁再锁动作行，这里反过来，等待会形成死锁。

**11. 内核契约的补充。** `AgentEngine` 增加 `retryToolCall`（恢复确认的重试）与 `reservedToolNames`（装配后的保留工具名，创建会话时校验自定义工具；内核未装配时取平台工具名与 harness 工具名）；`TurnContext` 增加 `interruptRequested`；`InboxPort.consumeSteer` 同时写 `session.message_consumed`。

**12. 审计。** outbox 主题 `audit`：`permission.decided`（每个工具调用的判定：`allowed`、`approved`、`denied` 随工具结果事件在同一事务写入；`ask` 在产生确认类动作时写入；无人值守的自动拒绝写 `denied`、来源 `unattended`）；`pending_action.concluded`（每个动作的结论：来源、结论、"记住此决定"的作用域、`decided_by`）。格式由 T16 定稿。

## 影响

- 架构设计：「端口」中 `AgentEngine` 的用途；「核心表」的 `pending_actions` 增加两列、新增 `permission_rules`；「平台中间件」增加 `InterruptCheckpointMiddleware` 并注明 steer 的顺序；「消息投递」「待处理动作」「权限判定」「子智能体」第 4 条补充本 ADR 的约定；版本 v1.7。
- 代码：`meridian-engine-spi`（`AgentEngine`、`ToolRetry`、`TurnContext`、`InboxPort` 说明）；`meridian-engine-agentscope`（`SteerMiddleware`、`InterruptCheckpointMiddleware`、`PendingInterrupt`、`ToolRetryContext`、`AgentScopeEngine`）；`meridian-runtime`（`approval` 全部、`delivery.app.EventIntake`、`dispatch.app.NodeChannel`/`NodeChannelListener`、`session.app` 的准备、执行与收尾，迁移 `V0004`）。
- T10a：文件工具的 `matchRule` 按第 2 条解释 `**`；工具基类优先使用 `ToolRetryContext` 的幂等键；实现 `generateSuggestions`（D21）。T12a：bash 对受保护路径的保护。T13：`spawn_subagent` 使用 `TurnContext.subagentPolicies`。T15b：租户与项目策略、项目级"记住此决定"迁到 control-plane；默认智能体配置要显式放行工具。T16：两种审计消息的格式。
- 风险：智能体配置漏掉 allow 规则时，`DEFAULT` 模式下每个工具调用都要确认；`unattended` 会话中的 `BYPASS` 智能体同样变为 `DONT_ASK`，需要 allow 规则才能用工具。
