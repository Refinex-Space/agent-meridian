## 背景

架构设计规定了数据访问按作用域分三类基类、ArchUnit 检查 `JdbcClient` 的使用者、`PlatformContext` 在 MVC 中用 `ScopedValue` 而在 runtime 中用 Reactor Context，但没有规定它们怎么实现。T02 要把这些能力一次落到 `meridian-common`、`meridian-persistence`、`meridian-security`，之后每个服务的仓储、后台作业、HTTP 入口都建立在它们之上，改起来代价很大，所以在这里记录。

需要定下来的问题：

1. 数据访问技术：统一用哪种方式写 SQL。
2. `TenantScopedRepository` 怎样做到"忘记带租户条件"在代码上写不出来，而不是靠约定。
3. `SystemRepository` 与 `@CrossTenant` 的使用规则，以及 `meridian-persistence` 自己的跨租户作业放在哪里。
4. `PlatformContext` 怎样从 Reactor Context 到达运行在虚拟线程上的 JDBC 调用。
5. Web 入口的公共能力（请求 ID、错误映射、`PlatformContext` 填充）放在哪个模块、怎样让 MVC 与 WebFlux 输出一致。

## 候选方案

**数据访问技术**

- A：Spring `JdbcClient`，SQL 用文本块写在仓储类中。
- B：JPA（Hibernate）。持久化上下文、脏检查与延迟加载让"一条语句改了什么"不可见，难以写出 `FOR UPDATE SKIP LOCKED`、`ON CONFLICT`、`WHERE lease_epoch = :epoch` 再检查影响行数这类调度与 fencing 必需的语句。
- C：MyBatis。SQL 写在 XML 或注解里，与仓储基类的租户约束分离，需要另做插件改写 SQL。
- D：jOOQ 或 Spring Data JDBC。前者需要代码生成且 PostgreSQL 特有语法支持受版本限制；后者以聚合为单位，同样遮住了 SQL。

**租户条件的强制方式**

- A：子类拿不到 `JdbcClient`，只能经基类的 `sql(...)` 得到语句包装 `ScopedStatement`；基类要求 SQL 引用命名参数 `:tenant_id`（项目级还要 `:project_id`），缺少即抛异常；这两个参数只从 `PlatformContext` 绑定，子类不能覆盖；上下文缺失时抛异常。
- B：约定子类自己在 WHERE 中加租户条件。无法检查，任务要求明确否定。
- C：查询构建器自动拼 WHERE。限制了 CTE、`SKIP LOCKED`、`ON CONFLICT`、分区表等写法。
- D：用 SQL 解析器（如 JSqlParser）改写每条语句。依赖重，对 PostgreSQL 特有语法不稳定，出错时难以排查。
- E：现在就启用 PostgreSQL 行级安全（RLS）。架构设计已把它定为二期的第二道防线（T37）；一期先做应用层的强制。

**上下文传递**

- A：`PlatformContexts` 统一提供两套读写：阻塞侧用 `ScopedValue`（JDK 25 正式特性），响应式侧用 Reactor Context（键为 `PlatformContext.class`）。`Blocking.call` 订阅时从 Reactor Context 取出上下文，在虚拟线程上用 `ScopedValue` 绑定后执行回调。仓储只读 `ScopedValue`。
- B：`ThreadLocal`。虚拟线程按请求创建时可用，但 Reactor 在线程间切换，必须处处手动设置与清除，泄漏风险高；编码规范已禁止。
- C：用 Micrometer context-propagation 在 Reactor Context 与 `ThreadLocal` 之间自动搬运 `PlatformContext`。依赖全局钩子，传递路径不可见；`ScopedValue` 的绑定是结构化的，无法由 `ThreadLocalAccessor` 写入。
- D：把 `PlatformContext` 作为参数逐层传给每个仓储方法。调用方容易传错租户，签名噪声大。

**Web 入口**

- A：`meridian-security` 的 `web` 包承担请求 ID、problem+json 映射，以及之后的认证与 `PlatformContext` 填充（T07、T14a、T14b）。映射逻辑 `ProblemMapper` 只有一份，MVC 用 `@RestControllerAdvice` 适配，WebFlux 用 `WebExceptionHandler` 适配（路由不存在、过滤器异常不经过控制器增强，只有 `WebExceptionHandler` 能覆盖）。
- B：各服务自己写异常处理。三个服务的错误格式会分叉，与编码规范「通用能力复用」冲突。

## 决策

### 数据访问

选 A：统一使用 `JdbcClient`，不引入 JPA、MyBatis、jOOQ、Spring Data JDBC。PostgreSQL 特有类型由 `persistence.jdbc.JdbcValues` 统一转换：`Instant` 写成 UTC 的 `OffsetDateTime`（驱动不接受 `Instant`），`jsonb` 写成 `PGobject`，`text[]` 传 `String[]`（传 `List` 会被 Spring 展开成 IN 列表）。

### 三类仓储基类

选 A，具体规则：

- 两类基类的构造参数是 `DataSource`，`JdbcClient` 在基类内部创建。这样 `JdbcClient` 只出现在基类的子类中，自动配置类也不需要引用它，ArchUnit 规则才能不留例外地执行。`JdbcClient.create(dataSource)` 经 `DataSourceUtils` 取连接，自动加入同一数据源上的 Spring 事务。
- `TenantScopedRepository` 的作用域在构造时声明：`PROJECT`（默认用途，绑定 `tenant_id` 与 `project_id`）或 `TENANT`（只绑定 `tenant_id`）。参数名是约定的命名参数，`tenants` 这类以 `id` 为租户键的表写成 `WHERE id = :tenant_id` 即可。
- 检查只保证 SQL 引用了作用域参数，不保证条件的逻辑正确：含 OR 的条件必须加括号。这一点由代码评审与二期 RLS 兜底。
- `SystemRepository` 的子类必须标注 `@CrossTenant(reason = "...")`；业务模块中的子类只能放在各上下文的 `infra.system` 包；`api` 包不能依赖它们。
- `meridian-persistence` 自己的跨租户作业（`OutboxWriter`、`OutboxRelay`、`IdempotencyPurger`）继承 `SystemRepository` 并标注 `@CrossTenant`，但不受 `infra.system` 位置约束：本模块就是基础设施层，不属于任何业务上下文。`ScopedStatement` 与基类同在 `persistence.tenant` 包，也豁免 `JdbcClient` 规则。
- 以上由 `meridian-arch-tests` 的规则 8 至 11 检查。

### 上下文传递

选 A。`Blocking` 使用 JDK 的每任务一个虚拟线程执行器，不设上限，并发度由连接池约束。MVC 服务运行在虚拟线程上，入口用 `PlatformContexts.run` 或 `call` 绑定，不需要 `Blocking`。BlockHound 测试证明 Reactor 线程上直接调用 JDBC 被检测为违规（`java.net.Socket$SocketOutputStream#write`），经 `Blocking` 调用则通过。

context-propagation 只用于把请求 ID 恢复到 WebFlux 的日志 MDC（`RequestIdMdcAccessor`），不用于传递 `PlatformContext`。

### Web 入口

选 A。problem+json 的响应体由 `ProblemMapper` 生成有序 Map，而不是 Spring 的 `ProblemDetail`：两种 Web 栈的 JSON 编码配置不同，Map 保证字段名与顺序完全一致。框架异常（Spring 的 `ErrorResponse`）保留状态码，detail 取错误码的标题而不是框架给出的英文说明，因为后者在两种 Web 栈中不同。5xx 的 detail 固定为不含内部信息的说明，排查以 `request_id` 关联日志。

### 同时确定的约定

以下细节影响多个模块，一并记录：

| 项 | 决定 | 理由 |
|---|---|---|
| problem+json 的 `type` | `urn:meridian:error:<code>`，例如 `urn:meridian:error:session.not_found` | 稳定、可由码值推出，不依赖一个需要长期维护的文档域名 |
| 分页游标 | `base64url(版本 + SHA-256 前 8 字节校验和 + 排序键)`，不签名 | 校验和拒绝截断、改动与伪造的游标，坏游标在入口得到 400；游标只决定从哪里继续读，数据范围由租户作用域仓储保证，签名需要的密钥分发不值得 |
| 不在「ID 规则」表中的内部 ID | outbox 消息、请求 ID 使用不带前缀的 ULID（`Ids.newUlid()`） | 前缀表是对外契约，内部记录不扩充它 |
| 请求 ID | 合法的传入 `X-Request-Id`（不超过 128 个字符的字母、数字与 `._:-`）沿用，否则生成 ULID；MDC 键 `request_id` | 便于跨系统串联日志；限制字符防止日志注入 |
| 幂等键作用域 | 主键 `(tenant_id, principal, idempotency_key)`，请求指纹为方法、路径、请求体的 SHA-256；处理中超过 5 分钟视为节点崩溃，允许接手 | 同租户不同调用方的同名键互不影响；不同项目的 API Key 不会重放彼此的结果 |
| outbox 投递 | 投递器每 500 毫秒运行，每批 100 条；已发布超过 7 天的记录每小时清理 | 用量与审计允许秒级延迟；防止表无限增长 |
| 本地与测试的 MinIO 镜像 | Chainguard 从 MinIO 源码构建的镜像，按摘要固定（RELEASE.2026-10-23） | MinIO 官方已停止发布容器镜像，Docker Hub 与 quay.io 均无法拉取；对象存储仍是 MinIO，客户端代码不受影响 |
| `meridian-test-support` 的依赖 | 不依赖 `meridian-persistence` | persistence 自己的集成测试要以 test 作用域依赖 test-support，反向依赖会形成 Maven 循环；迁移约定（`classpath:db/migration/<schema>`）在 test-support 中按同一约定实现 |

## 影响

- 架构设计无需修改条款。「租户隔离」中"只能放在各上下文的 `infra.system` 包"针对业务上下文，`meridian-persistence` 的豁免见上文。
- 编码规范「日志」的 MDC 键增加 `request_id`；「包与目录规划」中 `meridian-persistence` 的包增加 `objectstore`、`idempotency`，`meridian-common` 的包增加 `concurrent`。
- 各服务的第一个迁移复制 `outbox.sql`、`idempotency.sql` 片段（类路径 `cn/refinex/meridian/persistence/outbox/`、`.../idempotency/`）；设置 `meridian.persistence.schema` 后自动配置生效。
- 风险：占位符检查不能发现逻辑错误的 WHERE 条件；由代码评审、租户隔离集成测试与二期 RLS 兜底。
