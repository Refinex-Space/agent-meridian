# ADR-0043 身份提供方只认标准 OIDC，Keycloak 作为参考实现

## 背景

Q2 要求在 T14b 开工前决定控制台登录用自建 Keycloak 还是对接企业现有的 IdP。AgentMeridian 定位为通用平台，不为某一家公司定制：部署它的组织有的已有 IdP（Azure AD／Entra ID、Okta、Authing、Keycloak、ADFS 等），有的没有；有的 IdP 只支持 SAML 或 LDAP。选定任何一个具体的 IdP，都会让另一部分使用者无法接入，或者被迫多运维一个组件。

## 候选方案

1. **只支持自建 Keycloak**：实现最简单，但已有 IdP 的组织要再维护一套用户体系，账号、离职流程与公司现有体系脱节。
2. **只对接企业现有 IdP**：没有 IdP 的组织（小团队、试用、离线环境）无法登录，开发与测试也缺一个可控的 IdP。
3. **平台只认标准 OIDC，Keycloak 作为参考实现**：代码只依赖 OIDC 授权码加 PKCE、JWKS 校验与标准声明；本地开发、测试与"没有 IdP 的部署"用 Keycloak；已有 IdP 的组织改配置接入。代价是声明的映射（用哪个声明作用户标识、谁是平台管理员）必须做成配置，测试要覆盖不止一种配置。

## 决策

选方案 3。具体约定：

1. **只认 OIDC。** 控制台登录用授权码加 PKCE；服务端按签发方的发现文档与 JWKS 校验 access token（签名、`iss`、`aud`、过期）。签发方地址、受众、客户端 ID 都是配置项，代码中不出现任何 IdP 的专有接口或 SDK。
2. **SAML、LDAP 不进平台。** 只支持它们的 IdP 经 Keycloak 的身份代理（SAML）或用户联合（LDAP）转成 OIDC 后接入。
3. **声明映射可配置。** 用户标识默认取 `sub`，可改为其他稳定的声明（例如 Entra ID 的 `oid`）；显示名与邮箱取标准声明。平台管理员既可以按主体标识列表配置（T14a 已有），也可以按令牌中的组或角色声明配置（T14b 加，替代登记事项 D57 的待定项）。租户内的角色仍只来自 control-plane 的角色绑定，不从令牌映射（ADR-0042）。
4. **Keycloak 是参考实现，随项目提供。** Compose 的 `auth` profile 与仓库中的开发 realm（不含真实凭据）供本地与集成测试使用；Helm chart 把 Keycloak 作为可选组件（默认关闭），给没有 IdP 的部署使用（T28）。
5. **兼容性验证。** T14b 的测试至少用两种声明配置（默认 `sub`；改用其他声明加按组映射平台管理员）跑通，证明不依赖 Keycloak 的特有行为；接入具体商业 IdP 的说明写进部署文档（T26、T28），不作为一期的验收前提。

## 影响

- 架构设计：技术基线的"身份"一行改为"OIDC（标准协议接入，参考实现 Keycloak）"；「认证」中控制台用户一行补声明映射；「本地开发」的 `auth` profile；待决问题 Q2 标为已决。
- 任务：T14b 按本 ADR 实现（任务文件已注明）；T28 的 Helm chart 加可选的 Keycloak；登记事项 D57 改由 T14b 落实。
- 风险：各家 IdP 对 `aud`、组声明的格式不一致（例如组声明可能是 ID 而不是名称、超过数量后被截断），映射规则要容忍这些差异，并在部署文档中逐家说明。
