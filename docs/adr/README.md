# 架构决策记录

ADR（Architecture Decision Record）记录一项架构决策：当时面对什么问题、考虑过哪些方案、最终选了什么、要付出什么代价。它让一年后接手的人能看懂代码为什么是现在这个样子。

## 什么时候必须写 ADR

以下变更必须先提 ADR，评审通过后修改[架构设计](../architecture/architecture.md)，再改代码：

- 新增或替换技术基线中的组件，或升级其大版本。
- 新增部署单元。
- 修改模块依赖规则或端口。
- API 的破坏性变更。
- 修改架构设计中任何"必须"或"禁止"条目。
- M0 验证项不通过，需要调整方案。

## 流程

ADR 分两类，流程不同（判断标准见 `docs/plan/protocol.md`「决策分级」）：

- **补充型**（填补架构空白，不改变既定条款）：复制 [template.md](template.md) 为 `NNNN-短标题.md`，状态写"已采纳（补充）"，随任务直接提交。阶段评审（R1 至 R6）集中复核全部补充型 ADR。
- **变更型**（改动架构设计已定的内容）：状态写"提议"，提交后等待用户决定。用户采纳后状态改为"已采纳"，同时修改架构设计的相关章节与"架构决策记录"表，并递增架构设计的版本号。

编号取 `docs/adr/` 中最大编号加一，跳过下表中预留的编号。被新决策取代的 ADR 不删除，状态改为"已被 ADR-NNNN 取代"。
