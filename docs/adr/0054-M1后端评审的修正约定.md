## 背景

R2 对 M1 后端做了四个维度的独立审查（发现清单与逐条结论见 `docs/plan/R2-后端评审.md`）。确认的缺陷中，以下几条的修法收紧了授权、改变了幂等记录与清理作业的行为，或者补充了架构设计没有写到的数值，需要记录：

- **授权。** 租户管理员把待绑定的所有者邀请改成自己的邮箱，登录时就继承了所有者角色（I-01）；项目开发者登记 MCP 服务时可以任选租户级凭据、填自己的地址，探测与运行时把明文发过去（K-01）；只有 `actions:respond` 的审批人可以把"记住此决定"写进项目策略，而管理 API 上同一操作要 `AGENT_WRITE`（I-03）。
- **幂等记录。** 管理 API 把含 API Key、Webhook 签名密钥明文的响应体原样存进 `cp.idempotency_keys` 24 小时（K-02）；凭据写入与轮换的指纹不含值（ADR-0045 第 2 条有意排除），同键换值被当成重放（K-05）；控制台用户的公开 API 幂等主体不含项目，跨项目同键同体会拿到另一个项目的结果（I-05）。
- **后台作业。** outbox 发布目标短暂不可用时，最老的消息几秒内达到 10 次上限、永久停止投递（K-03）；会话清理按删除时间取一批，等待 Webhook 或失败的会话一直挡在队头（C-02），且删除后立即清理，执行中的轮次还在写（C-01）；用量记录写失败时 Redis 不结算（C-04）；读不到订阅的 Webhook 投递越过 24 小时截止仍会发送（C-08）。
- **接口。** WebFlux 的 JSON 请求体默认只聚合 256 KB，大上下文的对话补全与长消息被拒绝（A-04）；别的列表发出的游标让五个列表返回 500（A-02）；连通性测试与 MCP 探测把异常原文（内网地址、对端内容）回显给控制台（K-04）。

## 候选方案

**MCP 请求头的凭据**

- A：项目级资源只能引用项目级凭据。已有的、引用租户级凭据的 MCP 服务全部失效。
- B（采纳）：引用租户级凭据需要 `SECRET_WRITE`（所有者、租户管理员）；项目开发者只能引用管理员授给本项目的项目级凭据。修改时地址与请求头都没变不再检查，开发者仍能调整副作用等级。
- C：凭据登记允许的目标主机。更精细，但要改凭据的数据结构与管理接口，留给 T37。

**幂等记录中的一次性密钥**

- A：含密钥的响应不入库，重放返回 409。破坏"超时重试仍能拿到同一个 Key"的语义（control-plane 的不变量）。
- B（采纳）：响应体用租户数据密钥加密保存（`SecretCipher`，附加认证数据绑定租户、调用方与幂等键），重放时解密。凭据值以租户数据密钥派生的 HMAC 进入指纹：同键换值 409，库中的指纹不能离线穷举还原低熵的值。

**会话清理的队头**

- A：失败与等待时把会话挪到批次末尾（改 `ORDER BY`）。批次仍然可能被同一批会话占满。
- B（采纳）：`rt.sessions.purge_after`（rt `V0013`）：等待或失败的会话推迟 `purge-retry-delay`（默认 5 分钟），查询跳过它们。删除后至少等 `purge-delay`（默认 2 分钟，大于租约有效期与续租失败的放弃时间）再清理。

## 决策

1. **所有者邀请的邮箱。** 修改持有所有者角色的成员的邮箱需要 `OWNER_ROLE_MANAGE`；`member.updated` 的审计带邮箱与原邮箱。
2. **MCP 请求头的凭据。** 方案 B。
3. **审批人的"记住此决定"。** `remember_scope=project` 需要 `sessions:write`；只有 `actions:respond` 时只能记到本会话。回传自定义工具结果维持 ADR-0053（属于回应事件）。
4. **敏感写操作的幂等。** 方案 B，用于 API Key、Webhook 的创建，Webhook 签名密钥轮换，凭据的写入与轮换（`AdminRequests.writeSensitive`）。ADR-0045 第 2 条"指纹不含凭据值"改为"凭据值只以带密钥摘要进入指纹"。
5. **公开 API 的幂等主体。** API Key 取 Key ID；控制台用户取 `user:{主体}@{项目}`（`PlatformContext.idempotencyPrincipal()`）。
6. **outbox 的瞬时错误。** 发布目标不可用（`TransientFailures`：数据库与 Redis 的连接、超时、事务无法开启）不计消息的失败次数，释放本批剩下的认领并结束本批；只有确定性的错误计数，10 次后停止自动投递。`StreamConsumer` 与它共用同一判定。
7. **会话清理。** 方案 B。
8. **用量结算。** 用量记录对瞬时错误重试 2 次（退避 200 毫秒起）；无论记录成败都结算 Redis（计数反映已经消耗的 token），记录仍失败时错误交给调用方记日志，账本缺这一条（告警给 T27）。
9. **Webhook 截止时间。** 认领时已过 24 小时截止时间的投递不再发送，以 `deadline_exceeded` 结束。
10. **沙箱命令审计。** `sandbox.execute` 抛异常（连接中断、超时、取消）时同样写 `sandbox.command`，退出码 -1。
11. **请求体与错误。** runtime 的 JSON 请求体上限 10 MB（`spring.http.codecs.max-in-memory-size`）；游标的键缺失或类型不对是 400 `request.invalid_cursor`；连通性测试与 MCP 探测的说明只给分类（拒绝连接、超时、域名解析失败、TLS 失败、对端的 HTTP 状态码），原因链留在服务端日志；上传在表单阶段超限同样是 `file.too_large`。
12. **契约覆盖。** 测试客户端按真实路径匹配规范的路径模板记录被校验的操作（`meridian-test-support` 的 `contract.ContractCoverage`），每个服务排在最后的 `ContractCoverageIT` 断言本服务提供的操作全部被校验过。
13. **其他。** 删除从未使用的 `rt.sessions.budget_limit`（登记事项 D67）；runtime 的 `dev` profile 放行回环地址的 Webhook 接收方，与 control-plane 一致。

## 影响

- 架构设计：「授权」补 MCP 凭据引用与审批人"记住此决定"的限制；「凭据」补幂等记录的加密；「API 设计 / 约定」补幂等主体与请求体上限；「核心表」的 `sessions` 去掉 `budget_limit`、加 `purge_after`；「数据保留」补清理的等待与推迟；「计量与预算」补结算的重试；版本升至 v1.28。
- 迁移：rt `V0013`。已有的、由项目开发者登记且引用租户级凭据的 MCP 服务照常运行；之后修改其地址或请求头需要管理员。
- 角色矩阵：`createMcpServer` 改用项目级凭据，新增 `createMcpServer#tenant_secret`（只有所有者允许）。
- 风险：`purge-delay` 让删除到清理完成多 2 分钟，仍在"24 小时内清理"的承诺之内；幂等记录的解密依赖租户数据密钥，主密钥更换（D59）后 24 小时内的重放失败（返回 500），与凭据的处理相同。
