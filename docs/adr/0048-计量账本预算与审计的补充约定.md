## 背景

T16 在 control-plane 落地用量账本、审计日志与四级预算。架构设计规定了表名与主键（`usage_records`、`audit_logs` 按月分区，主键 `(id, occurred_at)`，审计只追加，保留 3 年）、outbox → Redis Stream → 消费者的数据流、四级预算的软硬阈值、每小时以账本为准对账、新租户默认零预算。ADR-0032 第 6 条把"是否换算为金额"留给本任务。以下几处没有写到，或按现状落不下去：

- **预算的单位与周期。** runtime 的 Redis 计数以 token 计、不分周期（登记事项 D24）。价格表按模型定价，币种在价格表上，同一租户的模型可以用不同币种；沙箱 vCPU 秒、搜索次数没有单价。
- **限额怎样到达 runtime。** "新租户默认零预算"要求没有配置时拒绝；四级里的会话由业务系统随时创建，不可能逐个设置。
- **对账的口径。** Redis 计数含尚未结算的预扣；账本落后于 Redis（outbox、Stream、消费者各有延迟）。直接"把 Redis 改成账本值"会把进行中的预扣抹掉。
- **分区由谁创建。** 应用角色 `meridian_app` 只有 DML，不能建表（`deploy/docker/postgres/initdb/10-meridian.sh`），默认权限还会把新分区的 `UPDATE`、`DELETE` 授给它。
- **审计消息的格式。** control-plane 的管理审计带 `actor`、`resource_type`、`resource_id`、`details`；runtime 的五种审计（`turn.finished`、`tool.executed`、`sandbox.command`、`permission.decided`、`pending_action.concluded`）是平铺的字段，没有操作者与资源。
- **outbox 的两处缺陷（登记事项 D49 C-12、D04）。** Relay 在持有行锁的数据库事务里调用 Redis；一条消息发布失败就 `break`，之后的消息全部等它（队头阻塞）。Stream 条目确认后不裁剪。

## 候选方案

**预算单位**

- A：金额。直观，但 runtime 预扣前要知道单价与币种，同租户多币种无法相加；沙箱与搜索没有单价也就不受预算约束，口径并不完整。
- B（采纳）：token（输入加输出），沿用 ADR-0032 的 Redis 计数。账本同时按价格表计价，报表给出金额；预算与币种无关。

**周期**

- A：不分周期，硬阈值是累计上限。租户、项目的预算用完只能不停调高。
- B：每条预算可配置周期。runtime 每次预扣前要先读周期才知道计数键，多一次往返。
- C（采纳）：固定规则：租户、项目、API Key 按自然月（UTC）重置，会话按整个生命周期。

**限额下发与默认值**

- A：runtime 经内部接口读限额并缓存。每次模型调用多一次查询或要处理缓存一致性。
- B（采纳）：control-plane 在提交后把限额写进每租户一个 Redis 哈希，每 5 分钟全量重写一次兜底；runtime 每次预扣用一次 `HMGET` 读四级。每级可以设置"该级所有范围的默认值"（`scope_id` 为空），具体范围的设置覆盖默认值；哈希里没有的级别按 0 处理。

**对账口径**

- A：Redis 改成账本值。进行中的预扣被抹掉，结算后计数偏少，下次对账又加回来，每小时都有"修正"。
- B（采纳）：目标值 = 账本 + 未过期的预扣。预扣记录带上它占用的计数键，对账时按键汇总；过期未结算的预扣不计入，正好被修正掉。修正用 `INCRBY 差值`，与并发的预扣、结算不冲突。

**分区的创建与保留**

- A：迁移中一次建好若干年的分区。不是"自动创建"，到期还要发版。
- B（采纳）：迁移角色拥有的 `SECURITY DEFINER` 函数：`cp.ensure_ledger_partitions(month)` 建两张表某月的分区并收回应用角色在审计分区上的 `UPDATE`、`DELETE`；`cp.drop_expired_ledger_partitions()` 删除早于 36 个月的分区，截止月份在函数内按数据库时间计算，应用角色不能借它删除更新的分区。应用角色只有这两个函数的 `EXECUTE`。

## 决策

**1. 预算以 token 计，按周期计数。** 计入预算的是模型调用（对话、压缩、Embedding、rerank）的输入加输出 token，与 runtime 预扣、结算的口径相同；沙箱 vCPU 秒与搜索次数只进账本，不占预算。租户、项目、API Key 的计数按自然月（UTC，周期键 `2026-11`），会话的计数不分周期（周期键 `total`）。Redis 键（`common.budget.BudgetKeys`，control-plane 与 runtime 共用）：

- 已用：`budget:{租户}:used:{级别}:{范围}:{周期}`，每次预扣把过期时间刷新为 62 天。
- 限额：`budget:{租户}:limits` 哈希，字段 `tenant`、`project:{ID}`、`project:*`、`api_key:{ID}`、`api_key:*`、`session:{ID}`、`session:*`，取值为硬阈值，`-1` 表示不限。
- 预扣：`budget:{租户}:rsv:{预扣 ID}` 哈希（`amount` 与 `keys`），预扣 ID 集合 `budget:{租户}:rsvs`；预扣 ID 带上预扣时的月份，结算按同一组键修正，跨月的调用不会改到下个月的计数。

**2. 默认零预算。** 一级的硬阈值取具体范围的设置，没有时取该级的默认值，再没有就是 0。新租户没有任何预算记录，所有模型调用以 `budget_exceeded` 结束；管理员设置后（四级都要有值，"不限"也要显式设置）才能使用。硬阈值为空表示不限；软阈值只产生告警。

**3. 账本。** 用量消费者按 outbox 消息 ID 与载荷的 `occurred_at` 插入 `cp.usage_records`（`ON CONFLICT DO NOTHING`），只在真正插入时在同一事务中累加 `cp.budget_usage`（每级每周期的账本汇总）。成本按记录中的价格表版本计算：未命中缓存的输入、缓存读、缓存写分别乘输入、缓存读、缓存写单价，非推理输出与推理分别乘输出、推理单价（缓存读写是输入的子集，推理是输出的子集），除以一百万；`numeric(24, 12)` 精确保存，不舍入；Embedding、rerank 只有输入。没有价格表的记录成本为空。计量种类：`model_tokens`、`embedding_tokens`、`rerank_tokens`、`sandbox_vcpu_seconds`、`search_calls`（本任务在 runtime 的联网搜索补齐），统一的 `quantity` 是 token 种类的输入加输出、沙箱的 vCPU 秒、搜索的次数；知识库存储量由 T18 增加种类。

**4. 软阈值告警。** 账本汇总越过软阈值（之前小于、之后不小于）时，在同一事务中插入 `cp.budget_alerts`（同一范围、周期、阈值只有一条）并写审计 `budget.soft_limit_reached`（outbox，经审计消费者入库）。调高软阈值后再次越过会产生新的告警。

**5. 对账。** 每小时一次，多实例经 PostgreSQL 咨询锁只运行一个：候选是本月有账本汇总的范围、最近 24 小时有用量的会话，以及 Redis 中本月与会话的计数键；目标值为账本加未过期预扣，差值不为 0 时 `INCRBY` 修正，写 `cp.budget_corrections` 并计指标 `meridian.budget.reconciliation.corrections`、`meridian.budget.reconciliation.correction.tokens`；修正量超过账本的 10% 且超过 1 万 token 时记 WARN（预扣逻辑可能有误）。账本落后于 Redis 的部分（消费延迟）会被临时修正掉，下一次对账加回。对账同时清理集合中已过期的预扣 ID。

**6. 审计。** 审计消息的标准字段是 `action`、`occurred_at`、`tenant_id`、`project_id`、`actor`（`{type, subject}`，`type` 为 `console_user`、`api_key`、`service`）、`resource_type`、`resource_id`、`session_id`、`details`；其余顶层字段并入 `details`。runtime 的五种审计补上操作者与资源：平台自己的判定与执行的操作者是 `service`/`runtime`，调用方回应待处理动作时是 `api_key` 或 `console_user`；资源分别是 `turn`、`tool_call`（工具调用 ID）、`pending_action`。`cp.audit_logs` 的写入只有审计消费者；应用角色在表与全部分区上只有 `INSERT`、`SELECT`。`cp.usage_records` 同样只追加，收回 `UPDATE`、`DELETE`。

**7. Stream 消费。** `meridian-persistence` 的 `StreamConsumer`：消费组 `control-plane`，消费者名取实例 ID；批量处理在一个事务中，失败时逐条重试，逐条仍失败且不是数据库瞬断的消息写 `cp.stream_dead_letters` 后确认（不阻塞后续消息）；空闲 60 秒以上的待确认消息由存活实例认领重投；确认后按消费组的最小待确认 ID（没有时取最后投递 ID）执行 `XTRIM MINID`（D04）。

**8. outbox 投递（D49 C-12）。** outbox 表增加 `claimed_until`、`attempts`：Relay 在短事务中以 `SKIP LOCKED` 认领一批（认领 30 秒）并提交，在事务外发布，再在另一个短事务中标记已发布；发布失败的消息 `attempts` 加一、释放认领，继续发布同批后面的消息，连续 3 条失败才结束本批（Redis 不可用）；`attempts` 达到 10 的消息不再自动投递，记 ERROR 等人工处理。实例在认领后崩溃，认领过期后由其他实例重新投递，整体仍是至少一次。

**9. 管理接口与公开接口。** 操作类别 `BUDGET_READ`、`BUDGET_WRITE`、`AUDIT_READ`（租户级，所有者与租户管理员）与 `USAGE_READ`（项目级，所有者、租户管理员、项目开发者、项目观察者）。预算 `/admin/v1/tenants/{t}/budgets`（增删改查，ID 前缀 `bdg`）、告警 `/budget-alerts`、租户用量报表 `/usage`、项目用量报表 `/projects/{p}/usage`、审计查询 `/audit-logs`；公开 `GET /v1/usage`（`sessions:read`，项目取自 API Key 或 `Meridian-Project`）由 control-plane 提供。报表按 `group_by`（`day`、`model`、`agent`、`api_key`，管理接口另有 `project`）聚合，总是按计量种类与币种分组（不同种类的数量、不同币种的金额不能相加），时间范围左闭右开，最长 366 天。

**10. runtime 的限额来源。** `meridian.runtime.model-routing.budget-source`：默认 `control-plane`（读上面的 Redis 哈希）；`file` 读 `dev-config/budgets`，只允许 `test` profile（单元与集成测试的夹具），`dev` 与生产都读 control-plane 下发的限额，本地脚本建租户后经管理接口设置预算。

## 影响

- 架构设计 v1.22：「核心表」补 `budgets`、`budget_usage`、`budget_alerts`、`budget_corrections`、`stream_dead_letters` 与分区函数，「跨服务数据流」补审计标准字段与消费语义，「数据保留」补分区删除方式，「计量与预算」补单位、周期、默认值、对账口径，「授权」补四个操作类别，「资源」补预算、用量与审计接口，「ID 规则」补 `bdg`。
- 迁移：cp `V0004`（新表、分区函数、权限、outbox 新列），rt `V0008`（outbox 新列），`meridian-persistence` 的 `outbox.sql` 同步（knowledge 的首个迁移复制它）。
- 代码：`common.budget`（级别与 Redis 键，runtime 的 `BudgetLevel` 移入）；`persistence.outbox.OutboxRelay`、`persistence.redis.StreamConsumer`；control-plane 新增 `metering`、`budget` 上下文，`audit` 上下文补消费与查询；runtime 的 `RedisBudgetLedger`、Lua 脚本、`RedisBudgetLimits`、审计消息、`TenantWebSearch` 的搜索计量。
- 风险：限额哈希的全量重写与管理接口的增量写入之间有竞态，旧值最长保留到下一次重写（5 分钟）；账本延迟期间对账会临时少算；会话计数 62 天无活动后过期，恢复使用时由对账补回。验证见 T16 的验收记录。
