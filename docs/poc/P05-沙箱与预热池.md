# P5 agent-sandbox、gVisor 与预热池

| 项 | 内容 |
|---|---|
| 状态 | 通过（T11） |
| 通过标准 | 预热池命中时认领 p95 小于 3 秒（架构设计「M0 技术验证」「非功能需求」）；快照、恢复、预热池补充的耗时有实测数据 |
| 环境 | Apple M1 Max，macOS arm64；Docker Desktop 29.4.2（Linux 6.12.76-linuxkit，10 vCPU，内存 8 GB，其中约 2.1 GB 被本机其他容器占用）；kind v0.33.0 单节点集群 `meridian`（Kubernetes v1.37.0，containerd 2.3.4）；Calico v3.33.0；gVisor runsc release-20261102.0（systrap 平台）；agent-sandbox v1.0.10（控制器与 Go 版 sandbox-router）；验证于 2026-11-08 |
| 被测对象 | `KubernetesSandboxDriver`（AgentScope 2.0.4 `KubernetesSandboxClient`，端口转发连接）、沙箱镜像 `agent-meridian/sandbox-runtime:0.1.0`（压缩后 270 MB，已经 `kind load` 预置在节点上）、chart `meridian-sandbox` 的 `values-kind.yaml` |

## 结论

通过。预热池命中时认领的 p95 为 223 毫秒，比目标 3 秒低一个数量级；50 次全部命中预热池。认领后预热池约 1.9 秒补回目标水位，预热池为 0 时冷启动认领约 2 秒。工作区 100 MB 时快照约 3 秒、恢复约 4 秒，本机的瓶颈是端口转发通道上的归档传输。

## 方法

测量代码为 `meridian-engine-agentscope-test` 的 `SandboxPoolMeasurementKindIT`（标签 `kind`），运行命令 `./mvnw -Pkind -pl meridian-engine-agentscope-test -am verify -Dit.test=SandboxPoolMeasurementKindIT`，原始结果写在 `target/p5/p5-results.json`。前提是 `scripts/dev/kind-gvisor.sh`、`install-agent-sandbox.sh`、`deploy-sandbox.sh` 已执行，`sandbox-small` 预热池 2 个，`medium`、`large` 为 0（`values-kind.yaml`：requests 取 limits 的 1/8）。

| 指标 | 做法 |
|---|---|
| 认领耗时 | 等预热池中未被认领且就绪的沙箱达到 2 个，记下它们的名字，计时调用 `SandboxDriver.create(small)`，断言得到的沙箱在记下的名字里（命中预热池）。耗时是驱动的全程：创建 `SandboxClaim`、等待控制器绑定沙箱并就绪、给 claim 打会话标签、建立到 sandbox-router 的端口转发、`start()`（在沙箱内执行一次 `mkdir -p /workspace`）。连续 50 次，每次测完删除沙箱 |
| 补充耗时 | 每次认领返回后，每 50 毫秒查询一次，到预热池中未被认领且就绪的沙箱回到 2 个为止 |
| 快照与恢复 | 沙箱内生成 100 个随机内容文件（10 MB 档每个 100 KB，100 MB 档每个 1 MB），计时 `snapshot`（沙箱内 `tar -cf`，经 `/download` 取回归档）；删除沙箱后计时 `restore`（认领新沙箱、经 `/upload` 传入归档、`tar -xf` 展开）；恢复后比对全部文件的 SHA-256 清单一致。每档 5 次 |
| 冷启动参照 | 预热池为 0 的 `medium` 认领 3 次 |

快照存储用内存实现（`InMemorySnapshotStore`），数据只计沙箱与 runtime 之间的传输，不含对象存储的写入与读取；runtime 的对象存储实现由 `ObjectStoreSnapshotStoreIT`（MinIO）验证功能。百分位按最近秩法取。

## 发现

1. **sandbox-router 是必需组件。** AgentScope 扩展的三种连接方式都经 router 转发，端口转发方式在沙箱命名空间中查找 `sandbox-router-svc`；v1.0.10 的发布清单不含 router。chart 把 router 部署在沙箱命名空间（ADR-0036）。
2. **模板默认的网络策略允许访问公网。** `networkPolicyManagement` 默认 `Managed` 且不写策略时，控制器生成"只允许公网"的默认策略。chart 改为 `Unmanaged` 并自带默认拒绝出网的策略；kind 实测沙箱内访问公网 IP 与解析域名都超时。
3. **emptyDir 挂载点上恢复快照失败。** 恢复时 `tar -xf … -C /workspace` 要设置归档根目录的时间与权限，挂载点属于 root，非 root 用户做不到，`tar` 以退出码 2 结束。镜像把 `/workspace` 改为指向 emptyDir 中由 uid 1000 创建的目录的符号链接后，快照与恢复通过（ADR-0036）。
4. **进程数上限在 gVisor 中按沙箱生效。** 入口脚本 `ulimit -u 256` 后，执行服务启动的命令在第 256 个进程处 `fork` 失败（`EAGAIN`）；一个沙箱占用 246 个进程时，另一个沙箱仍能启动 200 个（同为 uid 1000），说明计数不跨 Pod。
5. **Pod 安全。** 命名空间开启 Pod Security `restricted` 后沙箱 Pod 正常创建；Pod 内 `uname -r` 为 `4.19.0-gvisor`，uid 1000，有效 capabilities 为 0，根文件系统只读，`automountServiceAccountToken: false`。
6. **D03（Netty 4.2 与 Vert.x 4.5）。** fabric8 的 Vert.x 客户端在 Netty 4.2.19 上对 Kubernetes API 的创建、监听（watch）、合并补丁、删除与端口转发（WebSocket）均正常，登记事项 D03 关闭。
7. **内存占用。** 2.0.4 的扩展把快照归档整个读进内存（`Filesystem.read` 返回 `byte[]`，恢复时 `readAllBytes`），100 MB 工作区的快照或恢复在 runtime 侧占用约同等大小的堆，加上 `SnapshotStorePort.put` 的数组。runtime 的堆与并发回收数要按工作区上限估算，R1（P7 容量）复核。
8. **其他规格。** `medium` 预热池为 0 时冷启动认领成功；`large` 与 `medium` 的预热池在 8 GB 的 Docker 中装不下，按需扩容验证。

## 遗留

- 对象存储的写入与读取时间未计入快照与恢复，T12a 的空闲回收端到端测量时一并计入。
- 生产环境的连接方式（直连 router 服务或网关）与镜像拉取对冷启动的影响在 T28 部署时测量。
