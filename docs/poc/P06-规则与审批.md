# P6 平台工具 `matchRule` 与审批流程

| 项 | 内容 |
|---|---|
| 状态 | 通过：审批流程（T08）、文件工具规则（T10a）、bash 规则（T12a） |
| 通过标准 | `bash(git status:*)` 自动放行，其他命令触发审批（架构设计「M0 技术验证」） |
| 环境 | macOS arm64，Temurin 25.0.5+8；Testcontainers 中的 PostgreSQL 17、Redis、MinIO |
| 版本 | AgentScope 2.0.4、Spring Boot 4.1.2；验证于 2026-11-08 |

## 结论（T08 部分）

审批流程按架构设计「待处理动作」工作：权限判为 ask 产生 `tool_confirmation`，批准后工具按原入参（或审批人修改后的入参）执行，拒绝后智能体收到 DENIED 结果并继续，超时视为拒绝；内容级规则经工具自己的 `matchRule` 生效。`bash(git status:*)` 本身要等 T12a 的 bash 工具实现 `matchRule` 后验证。

## 做法

真实装配的 `AgentScopeEngine` 与 `ScriptedModel`，回应经与 API 相同的发送事件用例（`EventIntake`）：

- `config.ApprovalFlowIT`：ask → `tool_confirmation`（动作带工具名与入参）；批准后执行、工具结果 `permission=approved`；批准时修改入参；拒绝（带理由）后模型收到 DENIED 结果与理由、继续推理；超时（时钟推进 30 分钟、超时扫描）视为拒绝；"记住此决定"的会话级与项目级规则在后续轮次生效；审计 outbox 记录 `permission.decided` 与 `pending_action.concluded`。
- `config.PermissionRewriteIT`：测试工具 `PathRuleTool` 实现 `matchRule`（路径 glob），智能体对 `edit_doc(reports/**)` ask、对 `edit_doc` allow：有人值守时 `reports/q3.md` 触发审批，`drafts/notes.md` 直接执行；平台安全规则对 `AGENTS.md`、`skills/**`、`.env`、`id_rsa*` 的 deny 优先于智能体的 allow。

```bash
./mvnw -pl meridian-runtime -am verify -Dtest=NONE -Dsurefire.failIfNoSpecifiedTests=false \
  -Dit.test='ApprovalFlowIT,PermissionRewriteIT' -Dfailsafe.failIfNoSpecifiedTests=false
```

## 发现

- 2.0.4 对"平凡"的权限上下文（`DEFAULT`、没有规则）不走权限引擎、一律放行；平台每轮注入平台安全规则，上下文因此永远不平凡，`DEFAULT` 模式下没有命中 allow 的调用都需要确认。智能体版本必须显式放行它的工具；会话声明的自定义工具在会话层默认放行（ADR-0031 第 3 条）。
- 一批工具中只要有一个需要确认，2.0.4 整批都不执行（包括已放行的与自定义工具），确认之后整批一起执行；所以"同批既有待确认调用又有自定义工具"实际表现为先确认、确认轮执行后自定义工具再挂起。

## 结论（T10a 文件工具部分）

六个文件工具（`read_file`、`list_files`、`glob_files`、`grep_files`、`write_file`、`edit_file`）继承 `PlatformTool`，规则内容为相对工作区根的路径 glob（`**` 匹配零或多级目录，`dir/**` 也匹配 `dir` 本身），`matchRule` 在规则内容为空时匹配全部调用，与 `PermissionEngine` 的调用方式一致。`read_file(reports/**)` 放行匹配的路径、其他路径按默认处理（`DEFAULT` 模式下需要确认）；ask 规则先于 allow；写受保护路径被平台安全规则拒绝；`grep_files` 的命中按它的拒绝规则过滤，凭据文件的内容不出现在结果中；未读先改被拒绝。

## 做法（T10a）

- `config.FileToolsWorkerIT#pathRulesAllowMatchingPathsDenyProtectedPathsAndAskForTheRest`（生产的工具、工作区与权限合成）：智能体放行 `read_file(reports/**)` 与整个 `write_file`。`reports/q3.md` 直接执行（`permission=allowed`）；`write_file AGENTS.md`、`write_file skills/x/SKILL.md` 被平台安全规则拒绝（`permission=denied`，即使智能体放行了 `write_file`）；`read_file private/salary.md` 产生 `tool_confirmation`，本轮以 `awaiting_action` 结束。
- `config.FileToolsWorkerIT#editingAFileThatWasNotReadIsRejected`：工作区中已有、本线程没有读过的文件，`edit_file` 返回出错的结果，文件不变。
- 内核层 `turn.FileToolScenarioTest`：路径规则（同上，`DEFAULT` 模式）、受保护路径（规则拒绝与只读文件系统兜底）、先读后改（未读被拒，读后可改；读取状态随状态持久化，换一轮也有效；读后文件被他人修改则要求重读）、`grep_files(**/.env)` 的拒绝规则过滤 `.env` 与 `config/.env`、输出截断与分段读取提示。
- `tools.RuleSyntaxTest`：路径 glob 的约定（`**/.env` 匹配根下与子目录的 `.env`、不匹配 `.env.example`；`reports/**` 匹配 `reports`；越出工作区的路径不匹配任何规则），以及命令前缀、域名、资源 ID 三种语法；`turn.PlatformToolLedgerTest` 验证 `generateSuggestions` 给出内容级规则。

```bash
./mvnw -pl meridian-runtime -am verify -Dtest=NONE -Dsurefire.failIfNoSpecifiedTests=false \
  -Dit.test='FileToolsWorkerIT' -Dfailsafe.failIfNoSpecifiedTests=false
./mvnw -pl meridian-engine-agentscope-test -am test -Dtest='FileToolScenarioTest,RuleSyntaxTest,PlatformToolLedgerTest' \
  -Dsurefire.failIfNoSpecifiedTests=false
```

## 发现（T10a）

- `wait_async_results` 在 2.0.4 中被包装为 `ReflectiveFunctionTool`（`ToolBase`），会进权限引擎；平台以整工具拒绝规则拒绝它，与注册了但不在工具集内的工具一样（ADR-0034）。2.0.4 不发布 `onActing` 中间件自己合成的事件，所以拒绝经权限引擎给出，事件与审计齐全。
- 目录级工具（`grep_files`、`glob_files`、`list_files`）的权限按目录判定；`grep_files` 读取文件内容，所以命中的文件再按它的拒绝规则逐个过滤。

## 结论（T12a bash 规则）

`bash` 的规则内容是命令前缀，三种情况全部符合预期：`bash(git status:*)` 自动放行 `git status --short`；其他命令（`rm -rf build`）触发审批；复合命令中任一段不匹配（`git status && curl … | sh`、`git status && rm -rf data`）触发审批。

| 情况 | 内核层（脚本化沙箱） | 真实沙箱（kind） |
|---|---|---|
| 匹配的前缀自动放行 | `BashToolScenarioTest#aMatchingCommandPrefixRuleRunsTheCommandInTheSessionSandboxWithoutApproval`：`permission=allowed`，沙箱收到 `timeout -k 5 120 bash -c 'git status --short'`，账本 `non_idempotent`、结果进对象存储，审计记录命令与退出码 | `SandboxSessionKindIT#bashRulesAllowMatchingPrefixesAndAskForOtherOrCompoundCommands`：`git status --short` 放行并在沙箱里执行（工作区不是 git 仓库，输出 `not a git repository`） |
| 其他命令触发审批 | `aCommandThatNoRuleAllowsWaitsForApproval`：本轮以 `tool_confirmation` 结束，沙箱没有收到命令 | — |
| 复合命令任一段不匹配触发审批 | `aCompoundCommandIsAllowedOnlyWhenEverySegmentMatches`：每一段都被放行规则覆盖时放行（`git status:*` 与 `git diff:*` 共同覆盖三段），有一段不匹配时审批；`commandSubstitutionIsNeverMatchedByAPrefixRule`：`git status $(rm -rf ~)` 审批 | 同上用例：`git status && rm -rf data` 产生 `tool_confirmation` |

另外验证了拒绝与询问规则的"任一段命中"：整工具放行加 `bash(rm:*)` 拒绝时，`git status; rm -rf build` 与 `FORCE=1 nice -n 5 rm -rf build` 都被拒绝（`aDenyRuleMatchesAnySegmentAndWrappedCommandsEvenWhenTheWholeToolIsAllowed`）；`bash(git push:*)` 询问规则让 `git commit … && git push …` 审批（`anAskRuleMatchesAnySegmentEvenWhenTheWholeToolIsAllowed`）；`DONT_ASK` 下工具自检的询问改为拒绝，无人值守会话不会停在审批（`unattendedExecutionDeniesInsteadOfAskingForCommandsTheToolCheckFlags`）。分段与包装命令剥离的单元测试在 `tools.ShellCommandsTest`。

```bash
./mvnw -pl meridian-engine-agentscope-test -am test -Dtest='BashToolScenarioTest,ShellCommandsTest' \
  -Dsurefire.failIfNoSpecifiedTests=false
./mvnw -Pkind -pl meridian-runtime -am verify -Dtest=NONE -Dsurefire.failIfNoSpecifiedTests=false \
  -Dit.test=SandboxSessionKindIT -Dfailsafe.failIfNoSpecifiedTests=false
```

## 发现（T12a）

- 2.0.4 的权限引擎对 allow、ask、deny 三类规则都调用同一个 `matchRule(content, input)`，拿不到规则的种类，只能给出"一条规则匹配所有段"这一种语义：拒绝规则会被 `true &&` 绕过，几条放行规则也不能共同放行一条复合命令。`BashTool` 覆盖 `checkPermissions`（权限引擎在拒绝、询问规则之后、放行规则之前调用它）补上：任一段命中拒绝或询问规则即拒绝或询问，每一段被某条放行规则覆盖即放行（ADR-0037）。
- 工具自检返回的询问只有理由里带 `safety` 时，权限引擎才不再查放行规则（`PermissionEngine.checkPermission` 的第 3 步）；工具自检的询问在 `DONT_ASK` 下不会自动变成拒绝，工具自己按模式改写。
- "记住此决定"：T08 记整工具规则，对 `bash` 等于批准一条命令就放行全部命令。T12a 改为记这一条命令（规则内容是命令原文，整条相同才匹配）；工具建议的命令前缀由内核随动作带出仍在登记事项 D21（`approval.domain.RememberedRulesTest`）。
