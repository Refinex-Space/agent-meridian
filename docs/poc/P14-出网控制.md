# P14 出网代理按源 Pod IP 鉴权

| 项 | 内容 |
|---|---|
| 状态 | 通过（T12b） |
| 通过标准 | 白名单内的域名可以访问；其他域名被拒；沙箱删除后同 IP 的新 Pod 不继承旧授权；绕过代理的直连被 NetworkPolicy 阻断（T12b 任务的 P14 四条） |
| 环境 | Apple M1 Max，macOS arm64，Temurin 25.0.5+8；Docker Desktop（8 GB）；kind 单节点集群 `meridian`（gVisor 20261102、Calico v3.33.0、Pod 网段 `10.244.0.0/16`、agent-sandbox v1.0.10，`sandbox-small` 预热池 2 个）；出网代理 `envoyproxy/envoy:distroless-v1.40.2`；Testcontainers 中的 PostgreSQL 17、Redis、MinIO；验证于 2026-11-08 |
| 版本 | AgentScope 2.0.4、Spring Boot 4.1.2 |

## 结论

通过。沙箱的出网只能经过 Envoy 出网代理：代理对每个明文 HTTP 请求与 CONNECT 隧道带上 TCP 对端地址回调 runtime 的 `/internal/v1/egress:authorize`，runtime 按 `rt.sessions.sandbox_pod_ip` 找到会话与环境，按环境的白名单放行。白名单外的域名得到 403；沙箱删除后，在 30 秒缓存期内拿到同一 IP 的新 Pod 也得到 403；绕过代理的直连被网络策略拦截。

架构设计原定由 `ext_authz` 回调，实测它授权不了 CONNECT（见下文），改为 Envoy 内置的 Lua 过滤器回调（ADR-0038，已采纳）；其余细则见 ADR-0039。

## 做法

拓扑是"runtime 在宿主"（`values-kind.yaml`：`egressProxy.authz.topology: host`）：集群中的代理经 `host.docker.internal:18080` 回调测试进程中启动的 runtime。白名单内外的目标是 `deploy/kind/egress-echo.yaml` 中的 `allowed-echo` 与 `denied-echo`（同一个 Envoy 以 `direct_response` 应答服务名），不依赖公网。环境准备：

```bash
scripts/dev/kind-gvisor.sh meridian && scripts/dev/kind-verify.sh meridian
scripts/dev/install-agent-sandbox.sh meridian
scripts/dev/deploy-sandbox.sh meridian   # 沙箱 chart（含出网代理、网络策略）、回调凭据的 Secret、两个目标服务
```

用例 `meridian-runtime` 的 `config.EgressProxyKindIT`（标签 `kind`）：完整启动 runtime（`test` profile，端口 18080，开启会话沙箱），会话 A 的环境白名单只有 `allowed-echo.meridian-egress-test.svc.cluster.local`，经 `SandboxService.prepare` 从预热池认领真实的 gVisor 沙箱，在沙箱里执行 `curl`（沙箱模板的 `http_proxy` 指向代理）。

```bash
./mvnw -Pkind -pl meridian-runtime -am verify -Dtest=NONE -Dsurefire.failIfNoSpecifiedTests=false \
  -Dit.test=EgressProxyKindIT -Dfailsafe.failIfNoSpecifiedTests=false
```

## 结果

一次运行的输出（`curl -w` 打印状态码，隧道打印 `CONNECT 的状态码/状态码`，后面是响应体；会话 A 的沙箱 `sandbox-small-6wzkt`，Pod IP `10.244.27.149`）：

| 条目 | 命令（在沙箱中） | 输出 |
|---|---|---|
| 1. 白名单内可以访问 | `curl http://allowed-echo…/`（明文 HTTP，经代理转发） | `200 allowed-echo` |
| | `curl -p http://allowed-echo…/`（先 CONNECT 建隧道，HTTPS 的走法） | `200/200 allowed-echo` |
| 2. 其他域名被拒 | `curl http://denied-echo…/` | `403 egress to denied-echo… is not allowed for this sandbox` |
| | `curl -p http://denied-echo…/` | `403/000`（代理拒绝建立隧道） |
| 4. 绕过代理的直连被阻断 | `curl --noproxy '*' http://allowed-echo…/`（服务的 ClusterIP） | `000`（5 秒超时） |
| | `curl --noproxy '*' http://<echo Pod IP>:8080/` | `000` |
| | `getent hosts allowed-echo…`（DNS 仍可用，沙箱要解析代理的服务名） | 解析成功 |

条目 3（沙箱删除后同 IP 的新 Pod 不继承旧授权）：

1. 会话 A 的沙箱再访问一次 `allowed-echo` 得到 200，runtime 缓存了 `10.244.27.149` 的授权。
2. 立即删除会话 A 的沙箱（`SandboxService.deleteSessionSandbox`：删除 claim、清空 `sandbox_pod_ip`，提交后淘汰并广播该 IP 的授权）。
3. 旧 Pod 消失后，新建一个带沙箱标签的 Pod，用 Calico 的 `cni.projectcalico.org/ipAddrs` 注解拿到同一个 IP（预热池的补充 Pod 先拿到时直接用它）。新 Pod 在最后一次放行之后 4.6 秒就绪，仍在 30 秒缓存期内。
4. 新 Pod 访问 `allowed-echo`：`403`，runtime 的判定为 `unknown_source`（这个 IP 不属于任何会话）。旧授权没有被继承，而且不是靠 30 秒过期。
5. 把这个 IP 记到会话 B 名下（白名单只有 `denied-echo`，相当于会话 B 认领了这个 Pod，并按认领的流程广播失效）：新 Pod 访问 `denied-echo` 得到 `200 denied-echo`，访问 `allowed-echo` 得到 `403`，按新主人的白名单判定。

代理的访问日志（JSON，节选，`source` 是 TCP 对端地址）：

```text
18:08:18.403Z 10.244.27.149 GET     allowed-echo…     200 upstream=10.96.185.42:80
18:08:18.726Z 10.244.27.149 CONNECT allowed-echo…:80  200 flags=DC
18:08:18.799Z 10.244.27.149 GET     denied-echo…      403 upstream=None
18:08:18.899Z 10.244.27.149 CONNECT denied-echo…:80   403 upstream=None
18:08:29.824Z 10.244.27.149 GET     allowed-echo…     200            ← 删除沙箱前最后一次放行
18:08:34.208Z 10.244.27.149 GET     allowed-echo…     403 upstream=None   ← 同 IP 的新 Pod
18:08:34.305Z 10.244.27.149 GET     denied-echo…      200            ← 记到会话 B 名下之后
18:08:34.371Z 10.244.27.149 GET     allowed-echo…     403 upstream=None
```

失败即拒绝：runtime 没有启动时，从预热池中的沙箱经代理访问 `allowed-echo` 得到 `403`（Lua 回调连不上 runtime），隧道请求同样被拒（手工验证，2026-11-08）。

缓存失效的时序由集成测试覆盖（不依赖集群，T12b-A02）：`sandbox.app.SandboxEgressRevocationIT` 经真实的 `SandboxService` 回收、删除、重新连接（Pod 换了 IP）后，执行操作的节点立即拒绝旧 IP，另一个节点经 Pub/Sub 在 5 秒内拒绝；另一个节点在回收时断开了订阅，新会话认领同一 IP 时它仍会淘汰旧授权。`egress.app.EgressAuthorizerIT` 覆盖判定、两行同 IP 拒绝、30 秒过期、命中率指标。

## `ext_authz` 的实测（ADR-0038）

同一集群中，Envoy v1.40.2 的 `ext_authz`（HTTP 服务模式，`path_override: /internal/v1/egress:authorize`）把客户端请求的方法带进检查请求：明文 `POST` 的检查是 `POST`，CONNECT 的检查本身是 `CONNECT allowed-echo…:80 HTTP/1.1`（CONNECT 没有 `:path`，`path_override` 不生效）。授权服务对它返回 200，沙箱仍收到 403。`headers_to_add` 不能改写伪头（`:-prefixed or host headers may not be modified`），`disallowed_headers` 去掉 `:method` 后检查请求发不出去。默认还会把沙箱请求里的 `Authorization` 头转给授权服务。改用 Lua 过滤器后，四种情况（HTTP、CONNECT 各放行与拒绝一次）全部正确，授权服务收到的都是由脚本构造的 `POST /internal/v1/egress:authorize`。

## 遗留

- 沙箱可以向 CoreDNS 发任意域名的查询，CoreDNS 会转发到外部解析器，存在 DNS 隧道外带数据的可能（登记事项 D39，T37 评估）。
- 代理回调用的是开发期的静态服务凭据；T14b 换成服务 JWT 后，代理需要另定凭据方式（登记事项 D38）。
- 本次只在单节点 kind 上验证；多副本 runtime 的跨节点失效由集成测试覆盖。
