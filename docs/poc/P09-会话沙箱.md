# P9 外部 `SandboxContext` 与会话沙箱

| 项 | 内容 |
|---|---|
| 状态 | 通过（T12a） |
| 通过标准 | 两轮之间沙箱不停止；子线程能读到主线程写的文件；技能资源存在于沙箱中，被篡改后下一轮恢复（T12a 任务的 P9 三条） |
| 环境 | Apple M1 Max，macOS arm64，Temurin 25.0.5+8；Docker Desktop（8 GB）；kind 单节点集群 `meridian`（gVisor、Calico、agent-sandbox v1.0.10，`sandbox-small` 预热池 2 个），沙箱镜像 `agent-meridian/sandbox-runtime:0.1.0`；Testcontainers 中的 PostgreSQL 17、Redis、MinIO；验证于 2026-11-08 |
| 版本 | AgentScope 2.0.4、Spring Boot 4.1.2 |

## 结论

通过。会话沙箱由平台管理：runtime 在每轮调用内核之前准备好沙箱并落库，内核以 `SandboxContext.builder().externalSandbox(...)` 放进 `RuntimeContext`。harness 对外部沙箱不停止、不持久化（`SandboxManager` 的第 1 优先级，`release` 与 `persistState` 都跳过），所以沙箱跨轮次存活；同一会话的另一个线程拿到同一个沙箱，读到主线程写的文件；技能资源在沙箱中，被改动后下一轮开始时按摘要发现并重写。

## 做法

`meridian-runtime` 的 `config.SandboxSessionKindIT`（标签 `kind`）：真实装配的 runtime 节点（`WorkerFixture` 的平台模式加 `sandbox` 档：生产的 `PlatformToolProvider`（含 `bash`）、`PlatformWorkspace`、`SandboxService`、`DatabaseSandboxStates`、`TurnSandboxes`），`KubernetesSandboxDriver` 以端口转发连接 kind 集群，`ScriptedModel` 驱动。

```bash
./mvnw -Pkind -pl meridian-runtime -am verify -Dtest=NONE -Dsurefire.failIfNoSpecifiedTests=false \
  -Dit.test=SandboxSessionKindIT -Dfailsafe.failIfNoSpecifiedTests=false
```

| 条目 | 用例 | 观察 |
|---|---|---|
| 两轮之间沙箱不停止 | `bashAndFileToolsWorkInTheSessionSandboxWhichSurvivesBetweenTurns` | 第一轮 `bash` 写 `notes.txt`（输出含 `gvisor`、uid `1000`、`/workspace`）、`write_file` 写 `reports/q3.md`；第二轮 `cat` 读到两个文件。两轮后 `rt.sessions.sandbox_state` 的 `sandbox_id` 与 Pod IP 相同，集群中的 `SandboxClaim` 带会话标签 `meridian.refinex.cn/session-id` |
| 子线程能读到主线程写的文件 | `aChildThreadSharesTheSandboxAndTamperedSkillResourcesAreRestoredNextTurn` | 主线程 `echo from-main > shared.txt`；手工在同一会话插入子线程（`parent_thread_id` 为主线程）并为它入队一轮，子线程的 `bash` 读到 `from-main`（子智能体在 T13） |
| 技能资源存在且篡改后恢复 | 同上 | 智能体引用内置技能 `skills/builtin/docx`：`/workspace/.meridian/skills/docx/scripts/md_to_docx.py` 存在；一轮中 `echo hacked >` 改掉它，下一轮开始时 `syncSkills` 的摘要不一致，清空后重写，`head -1` 读到原文、不含 `hacked` |

内核层另有 `BashToolScenarioTest#theMainThreadAndAChildThreadUseTheSameSessionSandbox`（脚本化沙箱）：两个线程的命令进了同一个沙箱，harness 没有调用外部沙箱的 `stop`、`close`（替身会抛异常）。驱动层的 `KubernetesSandboxDriverKindIT#skillResourcesAreProjectedRewrittenWhenTamperedAndOutputsAreListed` 在真实沙箱中验证：第一次写入、第二次摘要一致不重写（平台算出的摘要与沙箱内 `sha256sum` 管道逐字节一致）、改文件或多出文件后重写、没有技能时删除目录、`SKILL.md` 不投影。

## 发现

1. **缺少外部沙箱时 harness 会自建沙箱。** `HarnessAgent.ensureSessionDefaults` 在 `RuntimeContext` 没有 `SandboxContext` 时用装配时的默认上下文，`SandboxManager` 走第 3、4 优先级，用规范中的客户端认领新沙箱，调用结束后停止并删除。平台给 `KubernetesFilesystemSpec` 配了一律拒绝的 `PlatformManagedSandboxClient`，漏注入时以异常结束而不是多出沙箱（ADR-0037）。
2. **共享实例上的沙箱绑定。** `SandboxBackedFilesystem` 先取本次调用上下文中的 `SandboxAcquireResult`，没有时退回实例字段（最后一次绑定的沙箱）；智能体实例被多个会话共享，这个退回会让工具操作别的会话的沙箱。平台工具的主文件系统外包 `SandboxWorkspaceFilesystem`，没有本次绑定就拒绝；直接调用工具的恢复确认重试由内核放入 `SandboxAcquireResult.userManaged`。
3. **沙箱文件系统的路径。** `BaseSandboxFilesystem` 把路径原样拼进 shell 命令，`CompositeFilesystem` 列根目录时向主文件系统传 `/`；平台路径 `/reports/q3.md` 要翻译为 `/workspace/reports/q3.md`，否则落到只读的容器根。`glob` 是 `find -name`，平台按 `RemoteFilesystem` 的语义在列出的文件上过滤。
4. **跨节点重新连接。** 序列化状态中的 `workspaceRootReady` 为真，另一节点 `resume` 后 `start()` 走"工作区保留"分支，不会用状态里的旧快照覆盖当前文件（`AbstractBaseSandbox.start` 的分支 A）。`SingleStartSandbox` 按 claim 名缓存在节点内，`start()` 只执行一次。
5. **耗时。** 五个用例共约 18 秒，其中每个会话第一轮认领一次沙箱（P5：p95 约 0.2 秒）；空闲回收与恢复的工作区约 1 MB。回收与获取在会话行锁内执行远程操作，持锁时长约为快照或恢复的耗时（P5：100 MB 约 3 至 5 秒）。
