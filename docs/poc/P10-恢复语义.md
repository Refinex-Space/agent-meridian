# P10 恢复语义：四种终止方式下的续跑

| 项 | 内容 |
|---|---|
| 状态 | 通过（T06；T08 用 `SteerMiddleware` 重跑 steer 部分） |
| 通过标准 | 强杀、出错、用户中断、停机四种终止下分别续跑，每种情况不重复用户消息，不丢 steer，不重复执行 `non_idempotent` 工具（架构设计「M0 技术验证」） |
| 环境 | macOS arm64，Temurin 25.0.5+8；Testcontainers 中的 PostgreSQL 17（pgvector + zhparser）、Redis、MinIO |
| 版本 | AgentScope 2.0.4、Spring Boot 4.1.2；验证于 2026-11-07 |

## 结论

通过。四种终止方式都按架构设计「崩溃恢复」续跑；验证过程中发现并修正了一个判定缺口：`lease_epoch` 每轮从 1 开始，只比较 `content_epoch` 会把上一轮的写入当成本轮的，导致丢掉用户消息。修正后状态写入同时记录所属轮次（`content_turn_id`），恢复按"本轮是否写过内容、写在哪次执行"判定（ADR-0028）。

## 做法

集成测试 `meridian-runtime` 的 `config.TurnRecoveryIT`。两个节点（`node-a`、`node-b`）各有一套完整的 Worker：调度、收件箱、工具账本、对象存储、真实装配的 `AgentScopeEngine`，共享数据库、Redis、MinIO、可控时钟与 `ScriptedModel` 的脚本（按调用顺序跨节点消费）。测试工具 `LedgerTool` 像平台工具一样在副作用之前记账、执行完记录结束，可以卡在执行中途，并统计跨节点的执行次数。

| 终止方式 | 模拟方法 |
|---|---|
| 进程被强杀 | 工具执行到一半时取消执行（不运行任何收尾）；工具在租约被接管之后才放行，它的结束记录写不进账本，与真实的进程被杀一致；时钟推进 31 秒，另一节点的回收器置回 |
| 出错 | 工具执行完后 `ScriptedModel` 抛出可重试的 `RateLimitTimeoutException`；关闭批次 checkpoint，恢复只靠 AgentScope 出错时保存的中途状态 |
| 用户中断 | 工具执行中写入 `turns.interrupt_requested_at`，续租读到后 Worker 调用 `AgentEngine.interrupt`；同时发来一条 queue 消息 |
| 优雅下线 | 启动 `node-a` 的后台循环（`TurnWorkerLifecycle`），工具执行中停止它（`AgentEngine.shutdown(60s)`），再放行工具 |

steer 的重新投递在 T06 用 `InboxPort.consumeSteer` 模拟失败那次执行的消费；T08 实现 `SteerMiddleware` 后在 `config.SteerRecoveryIT` 中重跑：steer 在第一批工具执行中途发来，由 `SteerMiddleware` 在第二次推理前真实注入，第二批工具执行到一半时强杀（见下文"steer 重跑（T08）"）。`TurnRecoveryIT` 的强杀用例同样改为由 `SteerMiddleware` 注入重新投递的 steer。

命令：

```bash
./mvnw -pl meridian-runtime -am verify -Dtest=NONE -Dsurefire.failIfNoSpecifiedTests=false \
  -Dit.test='TurnRecoveryIT,SteerRecoveryIT' -Dfailsafe.failIfNoSpecifiedTests=false
```

## 结果

| 终止方式 | 续跑结果 | 用户消息 | steer | 工具 |
|---|---|---|---|---|
| 强杀 | `node-b` 判定"本轮没有内容写入"，重放完整输入并附恢复说明（工具状态未知）；`recovery_attempt = 1`，`lease_epoch = 2`；指标 `meridian_turn_recoveries_total{mode="replay"}` 为 1 | 模型收到的消息中只有一条；状态中也只有一条 | 失败那次执行消费的 steer 恢复为待投递；T06 时本轮在注入前结束、它降级为 queue 成为下一轮；T08 起由 `SteerMiddleware` 在恢复的执行第一次推理前注入（排在恢复说明之后），`consumed_epoch = 2`，不再生成下一轮 | 没有重复执行 |
| 出错 | `node-a` 写 `session.error`（`retryable`）与 `session.status_rescheduled`（`retryable_error`），置回队列；`node-b` 判定"失败那次执行已保存中途状态"，输入为 `RecoveryOnly` | 只有一条 | 状态中已有，不重新投递 | `non_idempotent` 工具只执行一次；`node-b` 看到的上下文中 tool_use 与 tool_result 配对，恢复说明写明"已成功执行，不要重复执行"并附结果摘要 |
| 用户中断 | 本轮在下一次推理之前以 `interrupted` 结束（轮次 `interrupted`，`stop_reason=interrupted`），中断后没有再调用模型；中断期间到达的消息合并成新一轮并执行 | 新一轮中原消息只有一条 | — | 正在执行的工具执行完毕，不重复 |
| 优雅下线 | 轮次回到 `queued`，`recovery_attempt` 仍为 0，租户计数归零，只有一条 `session.status_rescheduled`（`node_shutdown`）；`node-b` 认领（epoch 2）后判定已保存中途状态，`RecoveryOnly` 续跑完成 | 只有一条 | — | 下线前完成的工具不再执行，上下文中 tool_use 与 tool_result 配对 |

同一测试类中的其他断言：

- 强杀时状态未知的 `non_idempotent` 调用：`node-b` 不执行本轮，创建 `recovery_confirmation` 待处理动作（`payload` 带幂等键与 `recovery_mode`，截止时间为 30 分钟后），轮次 `awaiting_action`，会话 `requires_action`，模型没有被再次调用，工具只执行过一次（T06-A06）。
- 连续两次强杀（第二个节点认领后还没执行就崩溃）后，`recovery_attempt = 2` 的认领不再执行，写 `session.error`（`turn.recovery_exhausted`，`exhausted`）与 `session.status_idle`（`error`），轮次 `failed`（T06-A07）。

恢复判定的全部分支另有单元测试 `session.domain.RecoveryPlannerTest`，包括"内容来自同一轮更早一次执行"（下线续跑后又被强杀）、恢复确认回应后的恢复说明合并、优雅下线不计入恢复次数。

## steer 重跑（T08）

`config.SteerRecoveryIT`：用户消息之后，第一批工具（查 a）执行中途发来一条 steer；放行后 `SteerMiddleware` 在第二次推理前注入（`consumed_epoch = 1`，写 `session.message_consumed`），模型发起第二批工具（查 b），执行到一半时强杀 `node-a`，`node-b` 回收后认领。

| 批次 checkpoint | 恢复方式 | steer |
|---|---|---|
| 关闭 | 本轮没有内容写入，重放完整输入（`mode="replay"`） | 被失败那次执行消费，恢复为待投递；恢复的执行在第一次推理前再次注入（`consumed_epoch = 2`），模型收到的消息与最终状态中各只有一条；两次执行各有一条 `session.message_consumed` |
| 开启（默认） | steer 注入后、同一次推理前进入 checkpoint（`SteerMiddleware` 排在 `BatchCheckpointMiddleware` 之外），本轮的内容来自失败那次执行，`RecoveryOnly`（`mode="recovery_only"`） | 已在状态中，不重新投递（`consumed_epoch` 仍为 1），恢复后只出现一次 |

两种情况都不丢 steer、不重复，用户消息只有一条，只有一个轮次。

## 发现的问题与处理

- **跨轮的 epoch 碰撞**：见"结论"。`LeaseFencingIT.contentWritesRecordTheirTurnBecauseEpochsRestartEveryTurn` 复现：上一轮 epoch 1 写入后，下一轮 epoch 1 的 `content_epoch` 也是 1。按轮次查询后，新一轮的内容写入为空。
- **强杀发生在结果事件写库之前**：恢复说明的结果摘要取不到已持久化的 `agent.tool_result` 事件，只能取账本中的结果引用。平台工具基类（T10a）在记录结束时应写入结果引用（登记事项 D14）；本测试的工具这样做了。
- **恢复确认之后的输入**：`replay_input` 模式下状态里没有本轮的输入，回应恢复确认时要重放原轮输入（登记事项 D13）。T08 已处理：恢复轮重放原轮输入并附恢复说明，`retry` 在调用内核之前用原幂等键重新执行，结果摘要写进说明（`config.RecoveryConfirmationIT`，ADR-0031）。
