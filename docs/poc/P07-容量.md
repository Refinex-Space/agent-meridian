# P7 单个 runtime 实例的容量

| 项 | 内容 |
|---|---|
| 状态 | 有条件通过（R1） |
| 通过标准 | 记录并发轮次与 SSE 连接上限（架构设计「M0 技术验证」）；目标值见「非功能需求」：单 Pod（4 vCPU / 8 GiB）300 个并发运行的轮次、3000 个 SSE 连接，事件从写入到推出 p99 低于 300 毫秒 |
| 环境 | MacBook Pro M1 Max（10 核、32 GB）；runtime 是宿主上的单个 JVM（Temurin 25.0.5，`-Xmx6g -XX:ActiveProcessorCount=4`，`dev` profile）；PostgreSQL 17.11、Redis 7.4.11、MinIO 在 Docker Desktop（8 GB）的 compose 中，经端口转发访问；脚本化模型服务与压测驱动也在宿主上 |
| 版本 | AgentScope 2.0.4、Spring Boot 4.1.2；测量于 2026-11-09 |

## 结论

有条件通过。修正一个线程池上限之后，单个实例在 4 核预算内达到了两项目标，瓶颈都在数据库侧而不在 CPU：

- **并发轮次：300 个（模型平均 3.5 秒）。** 300 个会话闭环执行，吞吐 71.5 轮/秒，没有失败；整轮耗时 p95 6.1 秒（脚本 2 至 5 秒），发送到 `session.status_running` p95 1.0 秒（含排队），事件推送延迟 p99 113 毫秒；runtime 进程 CPU 平均 1.6 核、峰值 2.1 核，堆不超过 600 MB。上限由**轮次启动速率**决定：单线程串行认领加 10 个数据库连接，单节点约 70 至 74 轮/秒，所以并发轮次上限约等于"70 × 平均每轮时长（秒）"。20 秒一轮时 1000 个会话同时约有 820 个轮次在执行，没有失败，但排队等待 p95 11 秒。
- **SSE 连接：默认连接池 2000 个、连接池 30 时 3000 个。** 100 个会话持续产生事件（含增量），2000 个连接每秒推送 1.6 万条，p99 189 毫秒；3000 个连接时数据库连接池（10）排队到 482、p99 746 毫秒，超过 300 毫秒的目标；连接池放到 30 后 3000 个连接 p99 127 毫秒、每秒 2.6 万条。5000 个连接时连接池 30 也排队（p99 950 毫秒）。瓶颈是每个连接每 5 秒一次的对账查询（N 个连接即每秒 N/5 次）。全部测量中没有连接失败。

条件：生产部署的连接池至少 30（PostgreSQL 的 `max_connections` 按 Pod 数规划，登记事项 D44）；要超过约 70 轮/秒的启动速率或 3000 个连接，需要并行认领与按会话共享对账（D45、D46）。

测量中发现并修正了一个缺陷：供应商流与平台工具在 Reactor 的 `boundedElastic` 上阻塞执行，它的线程数上限是 CPU 数的 10 倍（4 核时 40），300 个并发会话的吞吐停在 30 轮/秒、整轮 p95 22 秒。改到 `Blocking` 的虚拟线程后吞吐升到 71.5 轮/秒（ADR-0041 第 1 条）。另修正了安静会话的 SSE 响应头要等 15 秒的问题（第 2 条）。

## 方法

- **驱动**：`scripts/perf/CapacityDriver.java`，只用 JDK（`HttpClient` 与虚拟线程），经公开 API 驱动运行中的 runtime；`scripts/perf/capacity.sh <模式> [参数]` 运行。等效于 Gatling 的闭环负载：不引入新依赖，测量项（轮次时间点、事件信封的 `created_at`）需要解析平台的事件流。
- **模型**：脚本化模型服务（`scripts/dev/scripted-model.sh --scripts=scripts/perf/model-scripts`），脚本 `cap-2` 至 `cap-5` 各输出 200 个字符、分 25 块，块间延迟让整次调用分别约 2、3、4、5 秒，`cap-20` 约 20 秒。runtime 经生产的 `RoutedModel` 与 OpenAI 兼容客户端调用它，限流、预扣、计量照常经过。智能体 `agv_dev_scripted_1`（`dev-config/agents/scripted-chat.yaml`，没有工具）。
- **`turns` 模式**：N 个会话，每个会话一个 SSE 连接；发消息（随机选脚本）→ 从事件流等 `session.status_running` 与 `session.status_idle` → 下一轮。预热 20 至 45 秒后测量 60 至 90 秒。平均并发 = 各轮与测量窗口重叠的时长之和 ÷ 窗口时长。
- **`sse` 模式**：100 个会话按 `turns` 的方式持续产生事件（`cap-3`、`cap-4`），另以每秒 200 至 250 个的速度打开 M 个带增量（`?event_deltas=true`）的连接，均匀分到这些会话上。推送延迟 = 驱动收到的时间 − 事件信封的 `created_at`（同一台机器、同一时钟）。
- **采样**：每 5 秒读 runtime 进程的 CPU 与 RSS（`ps`）、actuator 的堆、Hikari 活跃与等待连接数、SSE 连接数、排队深度；另 `docker stats` 记 PostgreSQL 与 Redis。runtime 以 `--management.endpoints.web.exposure.include=health,metrics` 启动；Worker 的并发上限按场景调到 1000 或 2000（默认 300），开发租户的并发上限预先设为 2000（默认 20）。
- **CPU 预算**：宿主不能对单个进程限核，`-XX:ActiveProcessorCount=4` 只让 JVM 按 4 核设置线程池；"4 vCPU 预算内"以进程 CPU 不超过 400% 判断。8 GiB 的 Pod 按 75% 给堆（6 GiB）。

## 登记事项的核对

- **D19（SSE 每节点 100 毫秒轮询）**：推送延迟的 p50 约 60 至 90 毫秒、p99 不排队时 113 至 193 毫秒，Redis 容器 CPU 在 5% 以内。轮询间隔不是容量瓶颈，关闭 D19。
- **D31（`RemoteFilesystem` 的列举读出整个命名空间）**：本次的智能体没有文件工具，没有测量；会话文件多时的影响留给 T17b（工作区接口）与 T29 的压测，D31 改为 T29。
- **D36（快照归档读进堆）**：本次没有使用沙箱。按 P5 的数据，100 MB 工作区的快照约占同等大小的堆，回收器每批 20 个会话逐个处理，同一时刻只有一个快照在内存中；6 GiB 堆下不构成约束。并发回收与更大的工作区留给 T28 的部署配置，D36 改为 T28。
- **D41（子线程事件逐条写入）**：本次没有子智能体负载，改为 T29 的压测项。

## 发现

- **认领是单线程串行的**（`TurnWorkerLifecycle.drain` 一次认领一个，每次三步 SQL；按饱和吞吐推算每次约 13 至 14 毫秒）。单节点轮次启动速率约 70 至 74 轮/秒，连接池从 10 加到 30 只提高约 7%。多节点部署时总速率随节点数增加；单节点要更高时可以并行认领或一次认领多个（D45）。
- **SSE 的对账查询与连接数成正比。** 每个连接每 5 秒查一次会话的 `last_seq`；3000 个连接即每秒 600 次查询，与轮次执行争用连接池。可以改为按会话在读取循环中共享一次对账（D46）。
- **数据库连接池默认 10 偏小。** 连接池排队时，CPU 反而下降（3000 个 SSE 连接、连接池等待 482 时 CPU 只有 53%）。生产的连接池与 PostgreSQL 的 `max_connections` 需要按 Pod 数规划（D44）。
- **沙箱的远程操作在事务内占用数据库连接**（并发审查 C-02）：会话沙箱的获取与回收持有会话行锁执行远程操作，期间占住一个连接。本次没有沙箱负载，与 D44 一起规划。

## 复现

```bash
scripts/dev/up.sh
scripts/dev/scripted-model.sh --scripts=scripts/perf/model-scripts     # 另一个终端
JDK_JAVA_OPTIONS="-Xmx6g -XX:ActiveProcessorCount=4" scripts/dev/run-runtime.sh \
    --server.port=18080 --management.endpoints.web.exposure.include=health,metrics \
    --meridian.runtime.worker.max-concurrent-turns=1000   # 另一个终端；按场景加 --spring.datasource.hikari.maximum-pool-size=30
# 开发租户的并发上限默认 20：压测前在 rt.tenant_concurrency 中把 ten_dev 的 max_running 调高
scripts/perf/capacity.sh turns --sessions=300 --warmup=20s --duration=60s --runtime-pid=<runtime 的 PID>
scripts/perf/capacity.sh sse --sessions=100 --connections=3000 --ramp=250 --warmup=15s --duration=60s \
    --scripts=cap-3,cap-4 --runtime-pid=<runtime 的 PID>
```
