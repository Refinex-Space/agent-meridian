# P13 中间件执行顺序与压缩守护

| 项 | 内容 |
|---|---|
| 状态 | 通过（T04 测得链路，T09a 验证压缩守护） |
| 通过标准 | 平台中间件与 harness 中间件的实际执行顺序可测、符合设计；`CompactionGuardMiddleware` 的两层确实夹住 harness 的 `CompactionMiddleware`：预算耗尽时压缩被阻止，失败的摘要被拦截、不替换历史（架构设计「M0 技术验证」「平台中间件」） |
| 环境 | macOS arm64，Temurin 25.0.5+8；Testcontainers 中的 PostgreSQL 17、Redis、MinIO；真实模型 DashScope `qwen-plus` |
| 版本 | AgentScope 2.0.4、Spring Boot 4.1.2；验证于 2026-11-08 |

## 结论

通过。执行顺序完全由 `order()` 决定（数值大的在外层，相同的按注册顺序），`GracefulShutdownMiddleware` 由 AgentScope 固定放在最外层。压缩守护的外层取 20、内层取 0，夹住 order 为 1 的 `CompactionMiddleware`：链路测试断言了下标关系，三个行为场景证明了实际的嵌套——外层预检失败时压缩器没有发起调用；内层在压缩之后、推理之前看到新摘要；内层的 `contextWrite` 只覆盖推理调用，`RoutedModel` 据此把压缩器的调用记为 `purpose=compaction`。

对照实验确认了守护的必要性：去掉两层守护时，2.0.4 的压缩器吞掉模型异常，把 `(Summarization failed: …)` 当作摘要写进状态并继续推理，原始历史丢失。

## 实测的链路（外层在前）

`GracefulShutdownMiddleware`（固定最外层）→ `PlatformContextMiddleware`(300) → `PlatformTracingMiddleware`(200) → `LeaseGuardMiddleware`(100) → `RecoveryNoteMiddleware`(90) → `InterruptCheckpointMiddleware`(88) → `SteerMiddleware`(85) → `BatchCheckpointMiddleware`(80) → `ToolSpanMiddleware`(50) → `CompactionGuardMiddleware`(20) → `ContextCompositionMiddleware`(10，只用 `onModelCall`) → harness：`WorkspaceContextMiddleware`、`AtPathExpansionMiddleware`、`CompactionMiddleware`、`ToolResultEvictionMiddleware`、`InboxMiddleware`、`HarnessSkillMiddleware`（都是 1，按注册顺序）→ `CompactionGuardMiddleware.Inner`(0)。

span 层级（T04）：`turn` → `invoke_agent` → `chat {model}` 与 `execute_tool`（批次）→ `execute_tool {name}`。

## 源码核对（2.0.4）

- `CompactionMiddleware.onReasoning`：压缩成功后先 `applyToContext` 把 `AgentState` 的上下文换成"摘要加尾部"，再调用下游；所以内层只能在替换之后发现失败，必须用外层保存的副本恢复上下文再抛异常。随后的错误让 AgentScope 保存状态，保存的是恢复后的上下文。
- `ConversationCompactor.summarizePrefix`：模型异常被 `onErrorResume` 吞掉，返回 `(Summarization failed: …)`；模型返回空内容时是 `(Summary unavailable)`。两种都被内层拦截。摘要消息名为 `__compaction_summary__`，不卸载原文时正文前缀是 `Here is a summary of the conversation to date:`。
- 压缩器直接调用 `model.stream(...)`，不经过 `onModelCall`，但在同一条订阅链上：外层写进 Reactor Context 的 `CompactionWatch` 能被 `RoutedModel.doStream` 读到。
- 触发条件：动态阈值 = 窗口 − `reserved`（过小时取窗口一半），另有默认 50 条消息的条数阈值；平台关掉条数阈值（`triggerMessages(0)`），只按 token 触发。尾部保留下限 2000 token，会话不超过它时不压缩。
- `HarnessAgent` 的上下文溢出紧急压缩（`forceCompactAndRetry`，强制 `flushBeforeCompact`、`offloadBeforeCompact` 为默认的 true）只在 `call()` 路径上；平台用 `streamEvents`，不经过它，守护覆盖了平台实际使用的压缩路径。

## 做法与结果

内核层用真实装配的 `HarnessAgent`、平台中间件与 `RoutedModel`，底层供应商是 `ScriptedModel`，网关是 testkit 的 `InMemoryModelGateway`；模型目录的窗口 2000、压缩预留 500，第一轮约 1200 token、第二轮会话约 2400 token 时触发真实的 2.0.4 压缩（`CompactionGuardScenarioTest`）。

```bash
./mvnw -pl meridian-engine-agentscope-test -am test \
  -Dtest='MiddlewareChainTest,CompactionGuardScenarioTest' -Dsurefire.failIfNoSpecifiedTests=false
```

| 场景 | 结果 |
|---|---|
| 链路（`MiddlewareChainTest`） | 外层下标 < `CompactionMiddleware` < 内层；harness 的 6 个中间件按上面的顺序 |
| 正常压缩 | `agent.context_compacted(3, 3)` 出现在本次推理的 `span.model_request_start` 之前；压缩前预检 1 次；结算的用途依次为 `reasoning`、`compaction`、`reasoning`；压缩调用用平台摘要提示词、输入只有被压缩的第一条消息；状态中有摘要、没有第一条消息原文 |
| 预算耗尽 | 外层预检抛 `BudgetExceededException`，本轮 `session.error(model.budget_exceeded)` 加 `status_idle(budget_exceeded)`；压缩器没有发起模型调用，没有新的预扣，状态中没有摘要 |
| 摘要失败（供应商 400） | 内层抛 `CompactionFailedException`，本轮 `session.error(model.compaction_failed, terminal)` 加 `status_idle(error)`；之后不再发起推理调用；保存的状态含第一条与第二条消息、不含摘要与失败文本 |
| 摘要失败（供应商 503，重试用尽） | `CompactionFailedException` 的原因是 `ProviderUnavailableException`，事件映射沿原因链判为可重试：`session.error(retryable)` 加 `status_rescheduled(retryable_error)` |
| 对照：去掉两层守护 | 本轮照常 `end_turn`，状态中是 `__compaction_summary__` 加 `(Summarization failed`，第一条消息原文丢失 |

runtime 层用 Worker 完整路径与真实的 `RoutingModelGateway`（Redis 限流与四级预算、outbox 用量）：`ModelRoutingWorkerIT` 中压缩调用写了 `purpose=compaction` 的用量记录、计入会话预算（计数等于三条用量记录之和）、消耗了令牌桶的请求配额（每分钟 3 次的桶被三次调用用完）。

真实模型（`ModelLiveIT`，`qwen-plus`，窗口 3000、预留 500）：第二轮触发真实压缩（2.0.4 日志 `Compaction triggered: total=3 msgs / 3078 tokens, cutoff=1, keeping=2 msgs`），压缩调用输出非空，状态中的摘要不以失败文本开头，本轮 `end_turn`。

```bash
./mvnw -Plive -pl meridian-runtime -am verify
```

## 遗留

- 外层判断"本次会压缩"时用未裁剪的会话计数（裁剪只会减少 token），会话略高于阈值、裁剪后低于阈值时会多做一次预检；预检只检查不占用，没有副作用。
- 压缩失败会结束本轮；没有降级为"不压缩继续推理"，因为会话已超过阈值，继续推理大概率超出上下文。
