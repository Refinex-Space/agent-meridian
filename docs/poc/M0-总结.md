## 结论

M0 要证明的是：架构中依赖运行时行为、读源码无法确认的假设成立。逐项看，这些假设都成立了，其中 3 项需要调整方案并已经写成 ADR：AgentScope 不重试要写成 `maxRetries(1)`（P1，ADR-0023）、沙箱出网的授权回调授权不了 CONNECT 而改用 Envoy 的 Lua 过滤器（P14，ADR-0038）、P3 的批次 checkpoint 可行并默认开启（ADR-0028）。R1 的容量与内存测量（P7、P11）没有推翻任何设计，容量的瓶颈在数据库侧，可以靠连接池、并行认领与共享对账在 M1 中解决。

R1 的独立审查找出 2 个高严重度的安全缺陷（内部接口的认证可以被路径写法绕过、`sandbox` 档的 `@路径` 展开绕过权限）、2 个高严重度的正确性缺陷（一个被长时间锁住的轮次让整个节点的租约过期、工具执行被 5 分钟默认超时截断），压测又找出 1 个容量缺陷（模型调用并发被线程池限在 40），都已修复并有回归测试；中低严重度的发现中确认的问题已修复或登记到后续任务（[R1-评审发现](R1-评审发现.md)）。

## 实测数据与目标

| 目标（架构设计「非功能需求」与「M0 技术验证」） | 实测 | 来源 |
|---|---|---|
| 单 Pod 300 个并发运行的轮次 | 300 个（模型平均 3.5 秒，吞吐 71.5 轮/秒，0 失败，CPU 峰值 2.1 核）；并发上限约为 70 轮/秒 × 平均每轮秒数，20 秒一轮时约 820 个 | P7 |
| 单 Pod 3000 个 SSE 连接 | 连接池 10 时 2000 个、30 时 3000 个满足推送 p99；5000 个时连接池 30 也排队 | P7 |
| 事件从写入到 SSE 推出 p99 低于 300 毫秒 | 连接池不排队时 105 至 193 毫秒 | P7 |
| 从用户消息到 `session.status_running` p95 低于 500 毫秒（不含排队） | 低负载 106 毫秒；接近启动速率上限时含排队 1.0 秒 | P7 |
| 沙箱认领到可执行 p95 低于 3 秒（预热池命中） | 223 毫秒（kind 单节点，50 次全部命中）；快照 100 MB 约 3 秒、恢复约 4 秒 | P5 |
| 10 万个线程轮转后堆内存稳定 | Full GC 后的存活对象稳定在约 60 MB，空闲后 54 MB | P11 |
| 节点失联后 45 秒内被接管 | 逻辑由可控时钟的故障注入测试验证（30 秒租约后一个回收周期内置回队列并被另一节点认领）；真实时间的接管时长没有测量，留给 T29 的故障注入 | P2、P10 |
| API 可用性 99.9%、RPO 5 分钟、RTO 30 分钟 | M0 不涉及，T28、T29 验证 | — |

测量环境是一台 M1 Max 开发机：runtime 是宿主上的单个 JVM，按 4 核设置线程池、堆 6 GiB；PostgreSQL、Redis 是 Docker Desktop 中的单实例。宿主不能对单个进程限核，"4 核预算内"以进程 CPU 不超过 400% 判断；生产的 Pod 有网络往返与真实的 CPU 限额，T29 在 kind 部署上复测。

## 进入 M1 的前提

逐条列出，都不阻塞 T14a：

1. **Q2 企业 IdP 类型**在 T14b 开工前由你决定（自建 Keycloak 还是对接现有 IdP）。
2. **Q3 首批模型供应商与私有化推理服务**在 T15a 开工前由你决定；同时 T15a 要先完成 D52（`image.url` 的协议限制、密钥的租户归属与 `base_url` 校验），再引入 OpenAI 兼容之外的供应商类型（D25）。
3. **T28 的容量规划**要落实 D44（连接池至少 30、PostgreSQL 的 `max_connections` 按 Pod 数规划）、D45（并行认领）、D46（SSE 按会话共享对账），T29 复测 P7 的两项目标。
4. **P8 定稿**随 T19 完成（MCP Inspector 调通 `knowledge_search`）。
5. 登记事项 D47 至 D54 按建议的任务处理；其中 D51（安全加固）与 D50 中的产物下载竞态在 T37 之前，以沙箱与网络策略作为边界。
