## 2 API 一致性与契约覆盖（R2-A02）

- **实现与规范一致。** 三个服务的控制器都实现由规范生成的接口（`interfaceOnly` 加 `skipDefaultInterface`，少实现一个操作编译失败），代码里没有规范之外的路由；19 个内部操作的调用方限定与规范一致。
- **覆盖由测试断言。** 此前只有 runtime 的公开 API 与管理 API 有"每个操作都校验过"的断言，内部接口与 control-plane、knowledge 的公开操作没有，且操作名由测试自报。R2 新增 `meridian-test-support` 的 `contract.ContractCoverage`：三个服务的测试客户端每校验一次交互，就按真实路径匹配规范中的路径模板记下操作；每个服务排在最后的 `ContractCoverageIT`（`junit-platform.properties` 按 `@Order` 排类）断言本服务提供的操作全部被记到。覆盖面：公开 API 40 个操作（runtime 26、control-plane 3、knowledge 11）、管理 API 107 个、内部接口 21 个（runtime 4、control-plane 15、knowledge 2）。
- **风格。** 字段 snake_case、复数名词与短横线、游标分页形状与 `limit` 上下限三份规范一致；所有 POST 带 `Idempotency-Key`。不统一之处见下文审查 A 的发现，改动错误码与状态码会破坏契约，登记给 T26 在接入文档里写清（D91）。

## 3 页面到接口对照表（R2-A03）

逐行核对 `console-api-map.md`：接口、查询参数（会话筛选、项目级待处理动作、`session-stats`、投递记录的时间范围、用量明细的筛选、审计查询的筛选）与返回字段（`agents[].active_sessions`、`suggested_rules`、`last_check`、`revision`、`document_count`）都与规范和实现一致。两处字段不存在，已修正对照表：

- 「设置 / API Key」的"最后使用时间"：`ApiKey` 没有该字段，control-plane 也不记录（登记 D86）。
- 「知识库 / 文档管理」的"页数"：`KnowledgeDocument` 没有页数（Word 没有页码，D80），改为写入阶段与进度（`ingestion`）。

另外两处需要页面自行组合，不是缺口：会话头部的"用量"取最新一条 `session.usage` 事件的会话累计；事件时间线的"成本"按会话查 `P:/usage-records?session_id=`（`USAGE_READ`）。
