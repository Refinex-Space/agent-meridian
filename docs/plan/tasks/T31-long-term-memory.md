## 背景与目标

智能体在不同会话之间记住终端用户的偏好、项目的约定、自己积累的经验，是从"能用"到"好用"的关键一步。架构设计「记忆」一节规定了二期的做法：启用 harness 的记忆中间件，存储走平台存储，按"租户、项目、终端用户"隔离，写入经过准入判断，每条记忆可追溯，用户可以查看、编辑、删除。

## 必读

1. 架构设计「记忆」「工作区与沙箱」中的 `MeridianBaseStore`、「引擎装配」中关于记忆的行、「安全架构」。
2. 实现时查阅（AgentScope 源码，按需定位，不通读）：`MemoryFlushMiddleware`、`MemoryConsolidator`、`MemoryConfig`、记忆相关工具（`memory_search`、`memory_get`、`memory_save`）、`session_search` 系列只扫本地的问题。
3. `docs/plan/references.md`：记忆机制可参考 claude-code-analysis（只学机制）、spring-ai-agent-utils 的 AutoMemory、pi。

## 第一步：设计增补

在 `docs/architecture/addenda/M2-长期记忆.md` 写出设计增补：

- 记忆的作用域（终端用户、项目、智能体）与命名空间；跨租户绝不共享。
- 写入流程：何时触发 flush 与合并、准入判断（排除一次性信息与敏感字段；判断方式与误判处理）、每条记忆的来源追溯（会话、轮次、时间）。
- 读取流程：注入方式与上限、检索方式（是否需要语义检索；如需要，存储与索引设计）。
- 平台版的 `session_search` 系列工具：替换只扫本地磁盘的实现。
- API 与控制台：记忆的查看、编辑、删除；终端用户维度的批量删除（个人信息合规）。
- 与基线的关系：只补充，不改动"必须""禁止"条款；需要改动时写 ADR 提议并停止。

**设计关口**：设计增补提交后，把看板中本任务的状态改为"阻塞（等待用户确认设计增补）"，在报告中列出需要用户判断的设计取舍，然后停止（`docs/plan/protocol.md`「设计增补关口」）。用户确认后，用同一个任务编号新开会话续做实现。

## 范围

### 要做

- 设计增补中的全部内容：中间件启用与配置、存储、准入、追溯、工具替换、公开 API（`/v1/memory-stores` 或设计中确定的路径，写入规范）、控制台的记忆管理页面（遵循 `frontend-design.md`）。
- 真实模型测试：两次会话之间，智能体记住了终端用户在第一次会话中声明的偏好。

## 验收标准

- [T31-A01] 设计增补已写，且未改动基线条款（或已写 ADR 提议并停止）；用户已确认设计增补。验证：文件路径与确认日期。
- [T31-A02] 第一次会话中声明的偏好在第二次会话中被使用（`-Plive`）。验证：测试输出。
- [T31-A03] 不同终端用户、不同项目、不同租户的记忆互相不可见。验证：集成测试。
- [T31-A04] 准入：一次性信息与敏感字段（例如手机号、身份证号）不被写成长期记忆。验证：测试。
- [T31-A05] 每条记忆可追溯到产生它的会话与轮次；用户可查看、编辑、删除，按终端用户批量删除生效。验证：API 与控制台测试。
- [T31-A06] 平台版 `session_search` 系列工具基于平台存储工作，runtime 节点本地磁盘无会话数据。验证：集成测试。
- [T31-A07] 控制台记忆管理页面通过截图评审与禁用清单检查。验证：截图与评审记录。
- [T31-A08] 全部质量门禁通过。验证：命令输出。
